# 第一部分：上线前必须完成的代码开发

## 5. P0-01：重构租户与门店作用域权限

### 5.1 当前问题

`api/lib/permission.ts` 的 `loadPermissions()` 会把调用者所有 membership 的 role permission 合并成一个全局集合。

这会产生作用域串用风险：

```text
用户在租户 A 是管理员
用户在租户 B 只是普通员工
→ permissions 中仍包含租户 A 的管理员权限
→ 若同时拥有租户 B 某门店 membership，可能把 A 的高权限用于 B
```

`requirePermission()` 当前只分别检查：

- 权限码是否存在于全局集合；
- 是否有目标门店 membership。

它没有证明“这个权限码来自目标租户/门店的角色分配”。

### 5.2 目标设计

废弃全局权限 union 作为 Command 授权依据，新增：

```ts
interface AccessScope {
  userId: string
  employeeId: string
  tenantId: string
  storeId?: string
  roleIds: string[]
  permissions: string[]
  isPlatformAdmin: boolean
}

async function requireScopedPermission(
  c: Context<AppEnv>,
  requirement: {
    code: string
    tenantId: string
    storeId?: string
  },
): Promise<AccessScope>
```

处理顺序：

1. 根据 `auth.uid()`/user ID 查 active employee；
2. 查目标 tenant 下的 role assignment；
3. 门店命令只匹配：
   - `store_id = 目标门店`；
   - 或明确的 tenant-wide role；
4. 只加载匹配 role IDs 的 permissions；
5. 校验目标门店确实属于目标 tenant；
6. 返回已确认的授权作用域；
7. 平台管理员必须是独立平台级授权，不允许通过普通租户 role 中的字符串模拟。

### 5.3 修改范围

```text
api/lib/types.ts
api/lib/permission.ts
api/middlewares/auth.ts
api/lib/request-context.ts
api/routes/*.ts
supabase/migrations/新增 migration
supabase/tests/rls_tenant_store.sql
```

### 5.4 验收

必须新增自动化用例：

```text
A 租户管理员 + B 租户普通员工
不能在 B 租户执行管理员命令

A 门店管理员
不能在同租户 B 门店执行门店管理员命令

tenant-wide 管理员
可以访问本租户全部门店

platform admin
只有明确平台角色时才可跨租户
```

## 6. P0-02：收口所有 service role 路由

### 6.1 当前问题

Hono 多数路由使用 `createServiceClient()`。service role 会绕过 RLS，因此每个路由都必须在查询或写入前完成服务端作用域校验。

当前存在多处模式：

```ts
await requirePermission(c, { code: 'xxx' })
service.from('table').insert({
  tenant_id: input.tenantId,
  ...
})
```

但没有先验证 `input.tenantId` 属于调用者。

当前明显需要审计的模块包括：

```text
api/routes/diagnostics.ts
api/routes/operations.ts
api/routes/catalog.ts
api/routes/clinical.ts
api/routes/customers.ts
api/routes/pets.ts
api/routes/billing.ts
api/routes/inpatient.ts
api/routes/inventory.ts
```

### 6.2 强制模式

所有 service role Command 必须使用：

```ts
const scope = await requireScopedPermission(c, {
  code: 'lab.request',
  tenantId: input.tenantId,
  storeId: input.storeId,
})
```

所有按实体 ID 操作必须：

```text
先查实体 tenant_id/store_id
→ 再授权
→ 再修改或调用 RPC
```

所有列表接口必须：

```text
从已授权 scope 生成 tenant/store filter
```

不得允许客户端自由传 tenant ID 后直接查询 service role。

### 6.3 特别检查

`GET /api/operations/reports` 当前接受 tenantId 查询参数，但没有调用 `assertTenantAccess()`。

类似接口必须统一整改。

### 6.4 验收

- 建立 service-role route security test；
- 对每个 route 记录 permission、tenant source、store source；
- CI 检查 `createServiceClient()` 周围是否有 scoped authorization；
- 不允许只依赖前端隐藏按钮。

## 7. P0-03：下线旧文件上传与删除接口

### 7.1 当前问题

当前同时挂载了：

```text
/api/upload
/api/files/delete
/api/files/upload-intents
/api/files/:id/complete
/api/files/:id/download-url
/api/files/:id/archive
/api/files/:id/delete
```

旧接口：

```text
api/routes/upload.ts
api/routes/files.ts
```

仍然：

- 通过 Vercel 中转 multipart/base64；
- 使用旧 `r2_files` 表；
- 返回 `R2_PUBLIC_URL`；
- key 不强制 tenant/store/domain 结构；
- 删除按 user_id 或 system_admin；
- 与新私有 files/attachments 模型并存。

这会让前端或旧页面绕过新文件安全模型。

### 7.2 目标

生产环境只保留：

```text
POST /api/files/upload-intents
POST /api/files/:id/complete
POST /api/files/:id/download-url
POST /api/files/:id/archive
POST /api/files/:id/delete
```

处理：

1. 搜索所有旧 API 调用；
2. 迁移到 FileUploader/FilePreview；
3. 删除生产路由挂载；
4. 若必须兼容，使用 feature flag，仅 staging 可启用；
5. 迁移旧 `r2_files` 数据到 `files`；
6. R2 bucket 设为私有；
7. 删除 `R2_PUBLIC_URL` 作为业务访问方式；
8. 对历史 URL 建立短期兼容策略。

### 7.3 验收

- 生产路由访问 `/api/upload` 返回 404/410；
- `/api/files/delete` 不再接受任意 key；
- 所有新文件 key 包含 env/tenant/store/domain；
- 下载只通过短期签名 URL；
- 跨租户文件 ID 返回 403/404。

## 12. P0-08：修复库存预留与发药一致性

### 12.1 当前风险

migration 24 增加 reserve/confirm/release，`dispense_inventory` 使用 FEFO 和行锁。

但仍需要统一业务语义：

```text
reserve_inventory
→ prescription/payment 状态变化
→ confirm_inventory_reservation
或
release_inventory_reservation
```

必须明确实际发药是否：

- 直接调用 dispense；
- 先 reserve，再 confirm；
- confirm 是否再次扣 `quantity_on_hand`；
- 退款、取消、病历修订时如何释放。

### 12.2 开发要求

- 只保留一种正式发药路径；
- reservation 必须关联处方/收费单；
- 状态转换中自动释放过期 reservation；
- `available = on_hand - reserved` 始终非负；
- 幂等键唯一；
- 并发使用数据库锁；
- 不允许前端先读余额再自行判断。

### 12.3 验收

并发场景：

```text
库存 10
两个请求同时预留 8
只能一个成功

重复 confirm
只扣一次

取消处方
reserved 正确释放

支付失败
不产生永久占用
```

## 13. P0-09：把 E2E 改成真实闭环

### 13.1 当前问题

`closed-loop-a.spec.ts` 虽然命名为闭环 A，但实际存在：

- 多个独立 test，共享变量；
- 没有 `test.describe.configure({ mode: 'serial' })`；
- 后续步骤没有可靠复用前一步创建的实体；
- 创建预约没有明确选择刚创建的客户/宠物；
- 候诊、病历、处方、收费、发药多数只是验证页面和表格出现；
- 没有断言数据库状态；
- 闭环 B、闭环 C spec 不存在。

因此当前不能称为“核心闭环 E2E”。

### 13.2 目标结构

建议使用一个串行测试或 fixture：

```ts
test.describe.configure({ mode: 'serial' })

test('闭环 A', async ({ page, request }) => {
  // 完整流程
})
```

每个闭环保存真实业务 ID，并在末尾查询 API/数据库断言。

### 13.3 闭环 A 必须断言

```text
客户已创建
宠物归属正确
预约状态变化
候诊队列变化
encounter 创建
病历签署后只读
处方提交
invoice 金额正确
payment 过账
dispense movement 生成
inventory balance 正确减少
```

### 13.4 闭环 B

新增：

```text
e2e/tests/closed-loop-b-inventory.spec.ts
```

## 17. RLS 与 RPC 安全验证

运行 10 组 RLS SQL，并新增：

```text
rls_scoped_permissions.sql
rpc_direct_call_security.sql
service_route_tenant_scope.spec.ts
```

必须覆盖：

- 跨租户；
- 跨门店；
- 角色跨作用域复用；
- authenticated 直接调用 RPC；
- 伪造 operator ID；
- 伪造 tenant/store；
- audit；
- 文件下载；
- security definer；
- platform admin。

特别注意：

很多 RPC 被：

```sql
grant execute ... to authenticated
```

如果 RPC 内不校验 `auth.uid()` 和权限，浏览器可以绕过 Hono 直接调用。必须逐个分类：

```text
只允许 service_role
允许 authenticated 且内部完整鉴权
```

不应所有 RPC 统一授权给 authenticated。
