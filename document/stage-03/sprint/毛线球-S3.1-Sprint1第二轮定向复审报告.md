# 2. P0-01：resolveOperator() 没有按目标 tenant 解析，多租户员工账号会失败/取错作用域

当前 helper：

```ts
.from('employees')
.select('id, tenant_id')
.eq('user_id', user.id)
.eq('status', 'active')
.maybeSingle()
```

没有传：

```text
target tenantId
target storeId
```

这在单租户账号上通常工作，但毛线球的架构明确允许用户拥有多个 tenant/store membership。

如果同一个 auth user 在两个 tenant 都存在 active employee：

```text
employees:
user U → tenant A employee EA
user U → tenant B employee EB
```

那么：

```text
maybeSingle()
```

会因为多行返回失败。

结果：

> 合法的跨租户运营/医生账号无法执行合规 Command。

更糟的是备案 upsert：

```ts
const operator = await resolveOperator(service, c)
requireScopedPermission({
  tenantId: operator.tenantId
})
```

租户 scope 直接来自一个“未指定目标租户”的 employee 查询。

## 必须修

helper 改成：

```ts
resolveCurrentEmployee(
  service,
  c,
  tenantId,
  storeId?
)
```

调用顺序：

### 有实体的 Command

先：

```text
record / prescription / amendment
→ 查实体 tenant/store
→ requireScopedPermission
→ resolveCurrentEmployee(user, target tenant)
```

### veterinarian registration upsert

必须先由 **目标 employeeId** 或显式受控 tenant context 确定 tenant：

```text
target employee
→ tenantId
→ require tenant-level veterinarian_registration.manage
→ resolve current employee in that tenant
```

不能：

```text
随便取当前 user 的一个 employee
→ 把它的 tenant 当目标 tenant
```

# 3. P0-02：无可用仓库时，处方会“跳过库存扣减但仍标记 dispensed”

`dispense_prescription()` 当前：

```sql
if v_item.catalog_item_id is null or v_wh.id is null then
  v_skipped_items := v_skipped_items + 1;
  continue;
end if;
```

这个条件把两种完全不同情况混在一起：

### 情况 A

```text
catalog_item_id IS NULL
```

纯手工药名条目，没有库存绑定。

可以按产品规则允许不扣库存。

### 情况 B

```text
catalog_item_id 非空
但 v_wh.id IS NULL
```

说明这是库存商品，但目标 tenant/store 根本没有可用仓库。

当前却：

```text
skip
→ prescription.status = dispensed
```

这会产生：

> **实际没有任何库存出库，但处方显示“已发药”。**

这是医疗 + 库存账实一致性的 P0。

## 必须改

```sql
if v_item.catalog_item_id is null then
  -- 非库存手工药可按策略 skip
  continue;
end if;

if v_wh.id is null then
  raise exception 'DISPENSE_WAREHOUSE_NOT_FOUND';
end if;
```

并保证：

```text
处方仍 issued
库存不变化
整个 transaction rollback
```

同时测试必须覆盖。

# 4. P1/P0 Gate：R07 处方有效期仍未按验收规则完整实现

上一轮要求：

```text
validUntil > issuedAt
validUntil <= issuedAt + 3 days
默认“当日有效”按 tenant/store timezone
```

当前代码仍有两个问题。

## 4.1 没有检查 validUntil 不能在过去

`issue_prescription()` 当前只检查：

```sql
if p_valid_until > v_max_valid_until
  → VALIDITY_EXCEEDS_MAX
```

没有：

```text
p_valid_until > now()/issued_at
```

因此仍可以：

```text
现在开方
validUntil = 一小时前
→ issue 成功
→ 立即成为过期处方
```

这正是上一轮 R07 明确要求补的边界。

必须增加，例如：

```sql
if p_valid_until is not null
   and p_valid_until <= v_issued_at then
  raise PRESCRIPTION_VALIDITY_IN_PAST;
end if;
```

---

## 4.2 “最长 3 天”实现成了“开具日 + 第 3 个完整自然日结束”

当前：

```sql
date_trunc(local_day)
+ interval '4 days'
- interval '1 second'
```

假设当天 00:01 开具：

```text
最大有效期接近 96 小时
```

而不是：

```text
issued_at + 72 小时
```

这与本 Sprint 原验收规则：

```text
valid_until > issued_at + 3 days 必须拒绝
```

并不一致。

必须先统一产品/法规口径。

按已经确定的 Sprint 指令，建议直接实现：

```text
maximum = issued_at + interval '3 days'
```

默认值仍可以是：

```text
开具当地自然日结束
```

# 6. P1：veterinarian registration 权限模型与文档/角色授权不一致

当前 RLS 已明确：

```text

```

而 migration 26 已将：

```text

```

因此正常 store-scoped store_manager assignment：

```text
不能满足 tenant-level has_permission(..., NULL, ...)
```

但 migration 28 仍给 `store_manager` 写入：

```text

veterinarian_registration.manage
```

delivery 文档也写：

```text
store_manager 备案 read/manage ✔
```

实际后端 tenant-level Command 很可能拒绝普通 store_manager。

这不一定是安全漏洞，但属于明确的产品/权限不一致。

## 推荐

既然备案定义为 tenant-level：

只给：

```text
tenant_owner
tenant_manager
总部医疗管理角色
platform admin（平台场景）
```

备案 manage。

store manager 不要再声明“全权备案管理”。

如果店长确实要管理本店兽医备案，则数据模型应该增加 store relation，而不是 tenant-level permission 上硬塞 store role。
