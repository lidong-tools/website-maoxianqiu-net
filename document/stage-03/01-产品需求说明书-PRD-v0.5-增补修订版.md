# 【毛线球】产品需求说明书 PRD v0.5 — 增补与优先级修订版

> 日期：2026-08-07  
> 适用范围：毛线球多租户、多门店宠物医院 SaaS  
> 与 v0.4 关系：本文件作为 v0.4 的**增补与优先级覆盖层**；未被本文件修改的 v0.4 需求继续有效。  
> 当前工程阶段：Stage 02 收口——代码主体已铺开，重点转为基线对齐、权限收口、功能补全、staging 集成验证和真实闭环。

---

## 0. 文档规则

### 0.1 PRD 不再维护“模块完成度百分比”

“客户 75%”“审计 15%”等比例只适合作为一次性工程估计，不进入正式需求基线。

统一使用以下状态：

```text
not_started
in_development
code_complete
integration_pending
verified
production_ready
```

只有 `verified` 及以上，才表示真实业务场景已经通过。

### 0.2 冲突优先级

1. 已接受 ADR / 明确业务决策；
2. 本 PRD v0.5 增补；
3. PRD v0.4；
4. 状态机与数据模型；
5. UI/API 实现说明；
6. 旧系统操作手册。

# 1. v0.5 产品优先级

## 1.1 P0：Stage 02 收口与试用前必须完成

- 可验证交付基线：源码、线上、数据库版本一致；
- tenant / store / employee / role 作用域权限正确；
- RLS 跨租户、跨门店隔离通过；
- 客户 → 宠物 → 预约 → 接诊 → 病历 → 处方/执行 → 收费 → 库存主闭环通过；
- 病历与处方满足本文件合规约束；
- 关键敏感操作可审计；
- 日结与基础对账；
- 低库存、近效期等基础经营提醒；
- migration / RLS / E2E 能在 staging 重复执行。

## 1.2 P1：V1 商业增强

- 会员、储值、积分、套餐；
- 客户 360、客户分层、流失预警、回访任务；
- 门店/医生/护士/总部工作台；
- 完整采购和供应商；
- 高级报表和导出；
- 至少一个真实消息渠道；
- 打印模板产品化；
- C 端最小能力。

## 1.3 P2：规模化和差异化

- 多消息渠道；
- 高级营销自动化；
- PDF 存档和本地打印代理；
- 设备深度对接；
- AI 辅助书写与总结；
- 高级报表预计算/数据仓库；
- 在线问诊等需要独立合规评估的能力。

# 2. 多租户与组织补充

## 2.1 租户初始化向导（P0）

新租户首次启用应完成：

1. 创建租户主体；
2. 创建首个门店；
3. 设置营业时间、联系方式、时区；
4. 创建默认仓库；
5. 创建默认收银上下文；
6. 邀请首个租户管理员；
7. 初始化内置角色模板；
8. 初始化基础字典；
9. 初始化打印参数；
10. 生成初始化审计事件。

要求：

- 初始化流程必须幂等；
- 任一步失败不得留下可营业的“半初始化租户”；
- 租户停用、门店停业和归档不得物理删除历史医疗、收费、库存和审计数据。

# 3. 用户角色、权限与敏感操作

## 3.1 内置角色

至少提供：

- 租户所有者；
- 总部管理员；
- 门店店长；
- 前台；
- 医生；
- 护士；
- 药房；
- 检验员；
- 影像人员；
- 库管；
- 财务；
- 只读审计员。

## 3.2 权限作用域（P0）

权限判断必须绑定：

```text
user
+ tenant
+ store（需要时）
+ role assignment
+ permission code
```

不得把用户在租户 A 获得的高权限合并后用于租户 B。

## 3.3 敏感动作

以下动作使用独立权限码：

- 病历签署；
- 已归档病历特殊修改；
- 处方作废；
- 高额退款；
- 高额库存调整；
- 跨店调拨审核；
- 权限变更；
- 跨店医疗记录访问；
- 租户停用/恢复。

规则：

- 病历归档后的特殊修改必须审批并保留完整痕迹；
- 退款、库存调整、调拨采用“权限分离 + 可配置金额/风险阈值”；
- 达到阈值时申请人与审核人不得为同一员工；
- 不对所有门店、所有金额强制无差别双人审批；
- 所有审批结果进入审计。

# 5. 客户与宠物经营能力

## 5.1 客户 360

客户详情统一展示：

- 基本资料；
- 所有宠物；
- 最近到店；
- 预约；
- 就诊；
- 消费和欠款；
- 会员/储值；
- 疫苗/驱虫/复诊提醒；
- 沟通记录；
- 回访任务；
- 文件；
- 授权与营销订阅状态。

## 5.2 客户合并

要求：

- 支持重复客户候选；
- 合并前预览影响；
- 宠物、消费、就诊、提醒、文件等关系迁移；
- 不物理删除源客户；
- 保留 merge log；
- 合并操作使用独立权限。

## 5.3 客户分层与流失预警（P1）

首版采用可解释规则：

- 最近到店时间；
- 近 90/180 天消费；
- 就诊频次；
- 爽约；
- 疫苗/复诊逾期；
- 欠款。

可配置流失规则：

- 超过历史平均到店周期；
- 复诊逾期；
- 疫苗/驱虫逾期；
- 高价值客户长期未到店。

只生成“建议回访”，不得自动替代人工医疗判断。

## 5.4 回访任务

字段：

```text
customer_id
pet_id
source_type
source_id
task_type
scheduled_at
assignee_employee_id
status
channel
result
next_followup_at
```

状态：

```text
pending -> in_progress -> completed
pending/in_progress -> cancelled
```

消息发送成功不等于回访完成。

# 14. 消息与触达

新增要求：

- 预约提醒；
- 复诊提醒；
- 疫苗/驱虫提醒；
- 回访任务提醒；
- 失败重试；

- 失败原因；

MVP 范围说明（P0-07 决策，方案 A：消息退出 MVP）：

- 模板、投递记录、提醒扫描等数据能力保留，供后续版本启用。

V1 商业版至少接入一个真实渠道。

# 17. 动物诊疗监管合规（P0）

> 本节依据现行《动物诊疗机构管理办法》以及农业农村部公告第 734 号中的《动物诊疗病历管理规范》《兽医处方格式及应用规范》整理。商用前仍需复核最新国家与目标经营地区要求。

## 17.1 门（急）诊病历

至少包含：

- 动物主人/饲养单位信息；
- 病历号；
- 动物种类、性别、体重、毛色、年龄；
- 就诊时间；
- 主诉；
- 现病史；
- 既往史；
- 检查结果；
- 诊断和治疗意见；
- 医嘱；
- 检查报告；
- 影像；
- 病理资料；
- 知情同意书等关联资料。

要求：

- 接诊执业兽医师在就诊时完成记录并确认；
- 门（急）诊病历在就诊结束后 24 小时内归档；
- 归档前允许草稿；
- 归档后原则上禁止直接覆盖修改。

## 17.2 住院病历

必须支持：

- 入院记录；
- 连续病程记录；
- 每日病情变化；
- 重要检查结果；
- 诊疗措施和效果；
- 医嘱；
- 出院情况。

住院病历应在动物出院后 3 日内归档。

## 17.3 归档和修改

- 病历归档后原则上不得修改；
- 特殊修改需动物诊疗机构负责人批准；
- 必须形成 amendment / 新版本；
- 保留修改人、批准人、时间、原因和前后值。

建议字段：

```text
archived_at
archive_due_at
retention_until
signed_by_employee_id
signed_at
signature_method
amendment_reason
approved_by_employee_id
```

## 17.4 病历保存

病历保存不得少于 3 年。

病历关联的：

- 检验报告；
- 医学影像；
- 病理资料；
- 知情同意书；
- 其他病历附件；

其生命周期不得短于对应病历。

保存期满后的销毁需要审批和登记。

## 17.5 电子病历

系统必须：

- 具备身份认证；
- 为操作人员提供专有身份标识；
- 记录创建、修改、归档；
- 保存操作时间和操作人员；
- 历次操作可查询、可追溯；
- 病历查看也执行权限和审计。

可靠电子签名可作为后续 Provider 接入：

```text
signature_provider
signature_transaction_id
signature_certificate_ref
signature_verified_at
```

普通签名图片不得直接宣传为“可靠电子签名”。

## 17.6 兽医处方

处方必须：

- 关联本次诊疗和病历号；
- 保存动物主人与动物基础信息；
- 保存诊断；
- 记录药品名称、规格、数量、用法、用量；
- 记录开具执业兽医；
- 记录发药人员；
- 支持规定形式的签名/盖章/电子签名。

有效期：

- 默认开具当日有效；
- 特殊情况可注明延长；
- 最长不得超过 3 天。

字段至少：

```text
issued_at
valid_until
prescriber_employee_id
prescriber_veterinarian_ref
signed_at
dispensed_by_employee_id
dispensed_at
```

过期处方必须禁止执行发药。

## 17.7 处方保存

- 普通兽医处方至少保存 3 年；
- 兽用麻醉药品、精神药品、毒性药品处方至少保存 5 年；
- 特殊药品需要更长 `retention_until`；
- 销毁需要审批和登记。

## 17.8 合规验收

必须测试：

1. 门诊病历 24 小时归档；
2. 住院病历出院后 3 日归档；
3. 归档后直接编辑被拒绝；
4. 特殊修改生成 amendment；
5. 特殊修改需要负责人批准；
6. 病历 3 年 retention；
7. 普通处方 3 年 retention；
8. 特殊处方 5 年 retention；
9. 处方默认当日有效；
10. 延长期不超过 3 天；
11. 过期处方无法发药；
12. 非授权角色无法签署/开具；
13. 所有签署、修改和访问可审计。

# 18. C 端最小能力（P1，不阻塞 Stage 02）

不把 C 端升为当前 Stage 02 的 P0。

当前先预留数据模型，B 端和合规闭环稳定后再启动微信小程序/公众号等客户端。

首版范围：

- 客户身份绑定；
- 查看本人宠物；
- 在线预约；
- 查看已发布且允许客户查看的报告；
- 查看疫苗/驱虫/复诊提醒；
- 管理通知订阅；
- 查看会员/储值余额。

暂不做：

- 自动诊断；
- 未经医生确认的 AI 医疗建议；
- 任意查看内部完整病历；
- 在线自动开方；
- 复杂商城。

安全要求：

- 客户身份与员工身份分离；
- 客户与 customer 主档建立受控绑定；
- 家庭成员访问宠物需要授权关系；
- 报告必须 `published` 且 `customer_visible = true`；
- 医疗资料查看/下载进入审计；
- 解绑不删除历史医疗记录。

预留：

```text
customer_identities
customer_pet_access
customer_consents
notification_subscriptions
customer_visible
published_at
```

# 21. 对 Grok 规划建议的采纳结论

## 21.1 直接采纳

- 先收口再扩展；
- 合规前置；
- 核心业务闭环优先；
- 角色工作台；
- 日结对账；
- 客户 360；
- 流失预警和回访；
- 护士任务自动化；
- 审计能力提升；
- C 端架构预留。

## 21.2 已在 v0.4 存在，不重复造需求

v0.4 已经包含：

- 会员、储值和套餐；
- 消息模板及发送记录；
- 报表；
- 审计日志；
- 全局搜索；
- 数据导入；
- 打印配置；
- 多租户；
- 角色权限；
- 疫苗和驱虫；
- 检验；
- 住院；
- 文件附件。

v0.5 只补充其优先级、验收和业务细节。

## 21.3 调整后采纳

### C 端

纳入 P1/V1，不作为 Stage 02 P0 阻塞项。

### 双人审批

采用可配置阈值和职责分离；不对所有退款/调拨一刀切。

### 真实支付

Stage 02 不强制接支付网关，但必须支持外部流水号、日结、对账和幂等。

### AI

放在 P2。AI 输出必须由执业兽医确认，不得自动签署或自动开方。

## 21.4 不纳入正式 PRD

- 模块 40% / 60% / 80% 等主观完成度；
- 未经代码或测试证明的“已完成”；
- Mock Provider 视为生产能力；
- 页面存在视为业务完成。
