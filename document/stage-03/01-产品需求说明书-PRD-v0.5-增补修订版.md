# 【毛线球】产品需求说明书 PRD v0.5 — 增补与优先级修订版

> 日期：2026-08-07  
> 适用范围：毛线球多租户、多门店宠物医院 SaaS  
> 与 v0.4 关系：本文件作为 v0.4 的**增补与优先级覆盖层**；未被本文件修改的 v0.4 需求继续有效。  
> 当前工程阶段：Stage 02 收口——代码主体已铺开，重点转为基线对齐、权限收口、功能补全、staging 集成验证和真实闭环。
> 增补层：v0.5 为基线；v0.6 行业对标补漏（合规补强 + 客户增长 + 运营增强）已并入本文件，见 §17.9–§17.16 与 §23。本文件为毛线球唯一权威需求规范。

## 0. 文档规则

### 0.1 PRD 不再维护“模块完成度百分比”

“客户 75%”“审计 15%”等比例只适合作为一次性工程估计，不进入正式需求基线。

统一使用以下状态：

```text
not_started
in_development
code_complete
integration_pending
verified
production_ready
```

只有 `verified` 及以上，才表示真实业务场景已经通过。

### 0.2 冲突优先级

1. 已接受 ADR / 明确业务决策；
2. 本 PRD v0.5 增补；
3. PRD v0.4；
4. 状态机与数据模型；
5. UI/API 实现说明；
6. 旧系统操作手册。

# 1. v0.5 产品优先级

## 1.1 P0：Stage 02 收口与试用前必须完成

- 可验证交付基线：源码、线上、数据库版本一致；
- tenant / store / employee / role 作用域权限正确；
- RLS 跨租户、跨门店隔离通过；
- 客户 → 宠物 → 预约 → 接诊 → 病历 → 处方/执行 → 收费 → 库存主闭环通过；
- 病历与处方满足本文件合规约束；
- 关键敏感操作可审计；
- 日结与基础对账；
- 低库存、近效期等基础经营提醒；
- migration / RLS / E2E 能在 staging 重复执行。

## 1.2 P1：V1 商业增强

- 会员、储值、积分、套餐；
- 客户 360、客户分层、流失预警、回访任务；
- 门店/医生/护士/总部工作台；
- 完整采购和供应商；
- 高级报表和导出；
- 至少一个真实消息渠道；
- 打印模板产品化；
- C 端最小能力。

## 1.3 P2：规模化和差异化

- 多消息渠道；
- 高级营销自动化；
- PDF 存档和本地打印代理；
- 设备深度对接；
- AI 辅助书写与总结；
- 高级报表预计算/数据仓库；
- 在线问诊等需要独立合规评估的能力。

# 2. 多租户与组织补充

## 2.1 租户初始化向导（P0）

新租户首次启用应完成：

1. 创建租户主体；
2. 创建首个门店；
3. 设置营业时间、联系方式、时区；
4. 创建默认仓库；
5. 创建默认收银上下文；
6. 邀请首个租户管理员；
7. 初始化内置角色模板；
8. 初始化基础字典；
9. 初始化打印参数；
10. 生成初始化审计事件。

要求：

- 初始化流程必须幂等；
- 任一步失败不得留下可营业的“半初始化租户”；
- 租户停用、门店停业和归档不得物理删除历史医疗、收费、库存和审计数据。

# 3. 用户角色、权限与敏感操作

## 3.1 内置角色

至少提供：

- 租户所有者；
- 总部管理员；
- 门店店长；
- 前台；
- 医生；
- 护士；
- 药房；
- 检验员；
- 影像人员；
- 库管；
- 财务；
- 只读审计员。

## 3.2 权限作用域（P0）

权限判断必须绑定：

```text
user
+ tenant
+ store（需要时）
+ role assignment
+ permission code
```

不得把用户在租户 A 获得的高权限合并后用于租户 B。

## 3.3 敏感动作

以下动作使用独立权限码：

- 病历签署；
- 已归档病历特殊修改；
- 处方作废；
- 高额退款；
- 高额库存调整；
- 跨店调拨审核；
- 权限变更；
- 跨店医疗记录访问；
- 租户停用/恢复。

规则：

- 病历归档后的特殊修改必须审批并保留完整痕迹；
- 退款、库存调整、调拨采用“权限分离 + 可配置金额/风险阈值”；
- 达到阈值时申请人与审核人不得为同一员工；
- 不对所有门店、所有金额强制无差别双人审批；
- 所有审批结果进入审计。

# 5. 客户与宠物经营能力

## 5.1 客户 360

客户详情统一展示：

- 基本资料；
- 所有宠物；
- 最近到店；
- 预约；
- 就诊；
- 消费和欠款；
- 会员/储值；
- 疫苗/驱虫/复诊提醒；
- 沟通记录；
- 回访任务；
- 文件；
- 授权与营销订阅状态。

## 5.2 客户合并

要求：

- 支持重复客户候选；
- 合并前预览影响；
- 宠物、消费、就诊、提醒、文件等关系迁移；
- 不物理删除源客户；
- 保留 merge log；
- 合并操作使用独立权限。

## 5.3 客户分层与流失预警（P1）

首版采用可解释规则：

- 最近到店时间；
- 近 90/180 天消费；
- 就诊频次；
- 爽约；
- 疫苗/复诊逾期；
- 欠款。

可配置流失规则：

- 超过历史平均到店周期；
- 复诊逾期；
- 疫苗/驱虫逾期；
- 高价值客户长期未到店。

只生成“建议回访”，不得自动替代人工医疗判断。

## 5.4 回访任务

字段：

```text
customer_id
pet_id
source_type
source_id
task_type
scheduled_at
assignee_employee_id
status
channel
result
next_followup_at
```

状态：

```text
pending -> in_progress -> completed
pending/in_progress -> cancelled
```

消息发送成功不等于回访完成。

# 14. 消息与触达

v0.4 的模板、发送记录和触发场景继续有效。

新增要求：

- 预约提醒；
- 复诊提醒；
- 疫苗/驱虫提醒；
- 回访任务提醒；
- 失败重试；
- provider message id；
- 失败原因；

- 未配置真实 Provider 时必须禁用真实发送；
- 不得把 Mock 状态写为真实 `sent`；
- UI 显示“消息渠道未配置”。

MVP 范围说明（P0-07 决策，方案 A：消息退出 MVP）：

- 消息模块在本 MVP 阶段延期，不交付真实发送能力；
- 生产环境未配置 `MESSAGE_PROVIDER=real` 时，API 返回 `PROVIDER_NOT_CONFIGURED`，投递记录保持 `queued`，不得标记为 `sent`；
- 前端菜单与页面显示“消息渠道未配置”横幅；
- 模板、投递记录、提醒扫描等数据能力保留，供后续版本启用。

V1 商业版至少接入一个真实渠道。

# 17. 动物诊疗监管合规（P0）

> 本节依据现行《动物诊疗机构管理办法》以及农业农村部公告第 734 号中的《动物诊疗病历管理规范》《兽医处方格式及应用规范》整理。商用前仍需复核最新国家与目标经营地区要求。

## 17.1 门（急）诊病历

至少包含：

- 动物主人/饲养单位信息；
- 病历号；
- 动物种类、性别、体重、毛色、年龄；
- 就诊时间；
- 主诉；
- 现病史；
- 既往史；
- 检查结果；
- 诊断和治疗意见；
- 医嘱；
- 检查报告；
- 影像；
- 病理资料；
- 知情同意书等关联资料。

要求：

- 接诊执业兽医师在就诊时完成记录并确认；
- 门（急）诊病历在就诊结束后 24 小时内归档；
- 归档前允许草稿；
- 归档后原则上禁止直接覆盖修改。

## 17.2 住院病历

必须支持：

- 入院记录；
- 连续病程记录；
- 每日病情变化；
- 重要检查结果；
- 诊疗措施和效果；
- 医嘱；
- 出院情况。

住院病历应在动物出院后 3 日内归档。

## 17.3 归档和修改

- 病历归档后原则上不得修改；
- 特殊修改需动物诊疗机构负责人批准；
- 必须形成 amendment / 新版本；
- 保留修改人、批准人、时间、原因和前后值。

建议字段：

```text
archived_at
archive_due_at
retention_until
signed_by_employee_id
signed_at
signature_method
amendment_reason
approved_by_employee_id
```

## 17.4 病历保存

病历保存不得少于 3 年。

病历关联的：

- 检验报告；
- 医学影像；
- 病理资料；
- 知情同意书；
- 其他病历附件；

其生命周期不得短于对应病历。

保存期满后的销毁需要审批和登记。

## 17.5 电子病历

系统必须：

- 具备身份认证；
- 为操作人员提供专有身份标识；
- 记录创建、修改、归档；
- 保存操作时间和操作人员；
- 历次操作可查询、可追溯；
- 病历查看也执行权限和审计。

可靠电子签名可作为后续 Provider 接入：

```text
signature_provider
signature_transaction_id
signature_certificate_ref
signature_verified_at
```

普通签名图片不得直接宣传为“可靠电子签名”。

## 17.6 兽医处方

处方必须：

- 关联本次诊疗和病历号；
- 保存动物主人与动物基础信息；
- 保存诊断；
- 记录药品名称、规格、数量、用法、用量；
- 记录开具执业兽医；
- 记录发药人员；
- 支持规定形式的签名/盖章/电子签名。

有效期：

- 默认开具当日有效；
- 特殊情况可注明延长；
- 最长不得超过 3 天。

字段至少：

```text
issued_at
valid_until
prescriber_employee_id
prescriber_veterinarian_ref
signed_at
dispensed_by_employee_id
dispensed_at
```

过期处方必须禁止执行发药。

## 17.7 处方保存

- 普通兽医处方至少保存 3 年；
- 兽用麻醉药品、精神药品、毒性药品处方至少保存 5 年；
- 特殊药品需要更长 `retention_until`；
- 销毁需要审批和登记。

## 17.8 合规验收

必须测试：

1. 门诊病历 24 小时归档；
2. 住院病历出院后 3 日归档；
3. 归档后直接编辑被拒绝；
4. 特殊修改生成 amendment；
5. 特殊修改需要负责人批准；
6. 病历 3 年 retention；
7. 普通处方 3 年 retention；
8. 特殊处方 5 年 retention；
9. 处方默认当日有效；
10. 延长期不超过 3 天；
11. 过期处方无法发药；
12. 非授权角色无法签署/开具；
13. 所有签署、修改和访问可审计；
14. 受控药品无双人核对无法发药（§17.13）；
15. 未备案签名/签章的执业兽医师无法开具处方（§17.10）；
16. 疑似染疫宠物生成上报任务并可标记隔离措施（§17.11）；
17. 可生成诊疗废弃物交接台账并按期导出（§17.12）；
18. 门店可维护许可证信息并触发到期提醒（§17.14）；
19. 可一键生成年度合规报告并留痕（§17.15）；
20. 检验报告同人录入+审核被拦截、处方提交触发用药安全检查（§17.16）。

## 17.10 执业兽医师签名留样与电子签章备案

- **依据**：农业农村部 734 号公告"执业兽医师在备案单位签名留样或者专用签章、电子签名备案后，方可开具处方"。
- **现状**：PRD §17.1 仅"执业兽医备案门禁"，未建模签名留样 / 电子签章备案流程。
- **核心需求**：
  - 员工档案增加 `signature_specimen_ref`（手写签名留样扫描件）与 `e_signature_registration`（电子签章/电子签名备案号、备案机构、备案时间）。
  - 处方开具前置校验：该执业兽医师须已完成签名留样或电子签章备案，否则禁止开方。
  - 承接 §17.5 可靠电子签名 Provider 接入：备案号与 `signature_provider / signature_transaction_id` 关联。
- **验收**：未备案签名/签章的执业兽医师无法开具处方；备案信息可查可审计。

## 17.11 疫情 / 染疫上报

- **依据**：《动物诊疗机构管理办法》§25（发现染疫或疑似染疫立即上报，隔离消毒，不得擅治应扑杀疫病）。
- **核心需求**：
  - 新增"传染病上报"工作流：宠物风险标签含 `infectious`（PRD §294 已有），当就诊/检验标记为疑似染疫时，触发上报任务。
  - 记录上报动作（向农业农村主管部门 / 动物疫病预防控制机构）、上报时间、隔离消毒措施、是否疑似应扑杀疫病（拦截擅治）。
  - 不替代官方渠道，但系统须留痕并提醒责任人。
- **状态机**：`detected → reported → isolated → resolved / customed`（应扑杀疫病进入 `customed_blocked` 禁止治疗）。
- **验收**：疑似染疫宠物生成上报任务并可标记隔离措施；应扑杀疫病拦截治疗并告警。

## 17.12 诊疗废弃物处置管理

- **依据**：《动物诊疗机构管理办法》§26、《医疗废物管理条例》、四川省 2025-08 通知"规范诊疗废弃物处置"。
- **核心需求**：
  - 建立 `medical_waste_records`：废弃物类型（染疫动物及其排泄物、污染物、动物病理组织、锐器、药瓶等）、重量/数量、交接人、接收处理机构、交接时间、转运联单号。
  - 支持按"签约专业处理机构"登记，禁止随意丢弃；排放未经无害化处理的诊疗废水需记录。
  - 与诊疗活动关联（如手术、住院、化验产生的废弃物）。
- **字段要点**：`waste_type`、`quantity`、`handler_employee_id`、`disposal_org`、`handover_at`、`manifest_no`、`store_id`、`tenant_id`。
- **验收**：可生成废弃物交接台账并按期导出；审计记录创建/修改。

## 17.13 毒麻 / 精神 / 毒性药品专项管控

- **依据**：农业农村部 734 号公告、兽药管理条例、四川省 2025-08 通知"规范用药管理"。
- **现状**：PRD §17.7 仅规定"兽用麻醉/精神/毒性药品处方至少保存 5 年"，无管控流程——属关键遗漏。
- **核心需求**：
  - `catalog_items` / 库存增加 `is_controlled_drug` 标记与受控级别（麻醉/精神/毒性）。
  - 受控药品采购、入库、保管实行双人双锁 / 双签流程；发放需双人核对。
  - 空瓶 / 安瓿回收登记，与发药量对账。
  - 处方关联 `controlled_drug` 权限码（承接 ADR-MED-001），发药须二次确认并审计。
- **字段要点**：`is_controlled_drug`、`controlled_class`、`empty_vial_returned`、`double_check_by_employee_id`。
- **验收**：受控药品无双人核对无法发药；空瓶回收可对账；处方保存期按 §17.7 执行。

## 17.14 动物诊疗许可证生命周期管理

- **依据**：《动物诊疗机构管理办法》§13–§17（分支另办证、名称/法人变更、许可证公示、从业人员公示、监督电话公示）。
- **核心需求**：
  - 机构主数据增加 `practice_license`：许可证号、发证机关、诊疗活动范围、有效期限、公示状态。
  - 门店（store）与许可证绑定；兼营美容/寄养的须记录独立区域设置（§21 兼营独立区域）。
  - 分支门店提示"需另行办理许可证"；许可证临近到期提醒。
  - 前台公示组件：许可证 + 执业兽医资格 + 监督电话（可配置展示）。
- **验收**：门店可维护许可证信息并触发到期提醒；公示组件可渲染。

## 17.15 年度活动报告

- **依据**：《动物诊疗机构管理办法》§27、四川省 2025-08 通知"规范年度报告"。
- **核心需求**：
  - 提供年度活动报告生成器：汇总本年度诊疗量、处方量、受控药品使用、疫情上报、废弃物处置、员工备案等，形成可提交报告。
  - 报告按 tenant/store 维度生成，支持导出与提交状态记录。
- **验收**：可一键生成年度合规报告并留痕。

## 17.16 检验 / 处方双重审核（用药安全）

- **依据**：蘑菇宠医"处方双重审核（循证、防重复用药/配伍禁忌/超疗程/过度抗菌）"实践；用药安全合规趋势。
- **现状**：PRD 检验状态机不校验"录入人≠审核人"；处方无独立审核环节。
- **核心需求**：
  - 检验报告发布前强制"录入人与审核人不得为同一人"（关闭 ADR-MED-003 悬空决策）。
  - 处方提交时增加用药安全检查：重复用药、配伍禁忌、超疗程、过度抗菌提示（承接三案合并裁决 5 的"用药安全规则校验"列为 P1 处方提交检查）。
  - 高危处方可配置需第二人复核。
- **验收**：同人录入+审核被拦截；处方提交触发用药安全检查规则。

# 23. v0.6 行业对标补漏补充需求（P1 / P2）

> 本章已并入 v0.6 行业对标补漏方案（原 `02-补充需求方案-行业对标补漏.md`，现已归档至 `stage-03/_archive/` 作为采纳记录）。P0 合规七项已写入 §17.10–§17.16；本章承载 P1 客户增长与 P2 运营增强，作为 V1 及规模化阶段的需求基线。法规依据见 §22，竞品锚点见原归档方案 §6。

## 23.1 P1：客户与增长能力（行业标配，V1 商业增强）

### 23.1.1 宠主端小程序 / 客户门户（扩充 §18）

- **依据**：小暖 App、微宠医/蘑菇宠医小程序、全球 client portal（Digitail/Shepherd）。
- **现状**：§18 仅预留数据模型，C 端降为 P1。
- **核心需求**：在 §18 数据模型基础上，明确首版门户能力：在线预约、报告查看（published + customer_visible）、疫苗/驱虫/复诊提醒、会员/储值余额、健康档案摘要、消息中心。
- **范围**：微信小程序/公众号优先；安全规则沿用 §18 安全要求。

### 23.1.2 在线问诊生态对接（非自建）

- **依据**：小暖/微宠医/蘑菇宠医均提供线上问诊；本方案不新建问诊平台（阶段3 明确排除），但需"生态对接预留"。
- **核心需求**：定义问诊工单 ↔ 门诊就诊的转诊接口与数据映射（问诊结论可作为就诊主诉预填），不内置视频/诊断能力；由合作方提供问诊，毛线球承接线下转化与病历归档。
- **范围**：预留 `teleconsult_ref` 关联字段；不做自动开方。

### 23.1.3 LIS 化验设备直连

- **依据**：小暖已连接 2300 台化验设备；全球 IDEXX VetConnect PLUS。
- **现状**：PRD 检验仅有"外送检验工作流"，无设备直连。
- **核心需求**：定义 LIS 集成适配层——分析仪结果自动回传检验单（标本号/结果/参考范围/异常标记），减少手工录入；支持主流仪器协议适配（HL7/厂商 API）。
- **范围**：P1 先定义适配接口与 1-2 个主流仪器对接，不承诺全品牌覆盖。

### 23.1.4 私域营销引擎

- **依据**：小暖微信系统（会员卡/积分商城/优惠券/处方粮复购/健康提醒）、微宠医处方粮复购。
- **现状**：会员/储值/积分/套餐已有（P1）；消息模块退出 MVP（方案 A）；营销引擎列为 P1（市场调研 M-07）。
- **核心需求**：在消息模板与会员体系之上，提供营销活动管理（优惠券/满减/套餐包）、企微/社群触达占位、复购提醒（处方粮/驱虫/疫苗）、客户分层人群包。
- **范围**：内容生产与触达合规（短信/微信需真实 Provider，承接方案 A）。

### 23.1.5 宠物保险对接

- **依据**：小暖与中国人保/众安合作。
- **现状**：保险理赔材料 P1 预留，不直连结算（明确排除）。
- **核心需求**：定义理赔材料导出包（病历/处方/发票/检验结构化），供保险方调取；预留 `insurance_claim_ref`；不内置核保/直连结算。

### 23.1.6 中心药房 / 供应链集采（连锁）
