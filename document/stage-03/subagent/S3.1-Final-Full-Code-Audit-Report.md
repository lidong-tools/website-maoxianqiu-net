# 3. ✅ RPC ACL Final Lockdown 已真正实现

核心 Migration：

``` text
supabase/migrations/20260810000092_rpc_acl_final_lockdown.sql
```

本次全量源码确认该 Migration
不再是简单字符串搜索式"假安全检查"，而是通过 PostgreSQL Catalog：

``` text
pg_proc
regprocedure
```

对现有 Service-Role-Only RPC Overload 统一执行：

``` sql
REVOKE ALL ... FROM public;
REVOKE ALL ... FROM anon;
REVOKE ALL ... FROM authenticated;
GRANT EXECUTE ... TO service_role;
```

当前 Manifest 中敏感 RPC 的覆盖范围与 Migration 92 基本一致。

包括之前出现回归的：

``` text
create_invoice

approve_discount
review_record_amendment
publish_lab_results
review_lab_results
purchase RPCs
boarding RPCs
imaging RPCs
```

同时：

``` text
get_effective_membership_discount
```

也被额外收紧。

### 评价

这是正确的最终权限设计。

上一轮：

``` text
Feature Migration 后重新 GRANT authenticated
```

的问题在源码层已经被真正覆盖。

### 仍需 Runtime Gate

最终 Staging 必须执行真实数据库断言，例如：

``` text

EXECUTE = false

EXECUTE = false

EXECUTE = true
```

不能再仅依赖源码正则检查。

# 10. 为什么这是当前真正的 P0

对于单 Tenant 用户：

``` text

```

但对于：

``` text

```

可能出现：

``` text

旧 Route：

```

结果：

``` text

```

权限层可能阻止真正的跨 Tenant 数据泄漏，但业务页面仍可能：

-   查错 Tenant；
-   返回空数据；
-   误报无权限；
-   用错误 Store 列表；
-   产生极难诊断的多租户问题。

# 18. 正确修复

新增 Forward Migration。

UPDATE Policy：

``` text
USING:
status = 'draft'
AND permission

WITH CHECK:
status = 'draft'
AND permission
```

DELETE：

如果业务不允许删除：

``` text
直接取消 authenticated delete policy
```

或仅允许：

``` text
draft
```

更强方案：

增加 Trigger：

``` text
signed row
→ prohibit UPDATE/DELETE
```

仅受控 Amendment / Service Role 特殊流程例外。

医疗数据建议采用：

``` text
RLS
+
Trigger
```

双层防护。
