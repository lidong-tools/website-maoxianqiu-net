# 6. 🟠 跨 Tenant 切换时，少数页面仍可能保留旧 Tenant 快照

部分改造页面采用：

```ts
const currentTenantId = ref('')

onMounted(() => {
  currentTenantId.value = tenantStore.currentTenantId
})
```

而不是：

```ts
computed(() => tenantStore.currentTenantId)
```

或 Watch。

如果用户在当前页面中从：

```text
Tenant A / Store A
```

直接切到：

```text
Tenant B / Store B
```

Toolbar 的全局 Context 会改变，但页面自己的：

```text
currentTenantId
```

可能仍保留 A，直到页面重新挂载。

### 建议

统一：

```ts
const currentTenantId = computed(
  () => tenantStore.currentTenantId
)
```

Store-scoped 页面同时：

```text
watch currentTenantId/currentStoreId
→ reload
```

### 严重度

```text
P1 / 多 Tenant Pilot 前建议修
```

如果 Pilot 每账号只属于一个 Tenant，短期风险低很多。

# 7. 🔴 新发现：Migration Version 115 冲突

当前合并后的 Migration 同时存在：

```text
20260810000115_s3_1_source_gate_fixes.sql

20260810000115_messaging_idempotency_lockdown.sql
```

两个文件拥有相同 Migration Version：

```text
20260810000115
```

这是一个明确的集成错误。

Supabase Migration History 依赖唯一版本。

不能带着两个：

```text
115
```

进入：

```text
Blank DB Migration
Existing DB Upgrade
Staging
Production
```

# 8. Migration 冲突处理方式

如果这两个 115 **尚未在任何共享数据库执行**：

建议保留：

```text
115 messaging
116 analytics
```

并把 S3.1 Source Gate Fix 改成新的唯一版本，例如：

```text
117_s3_1_source_gate_fixes.sql
```

同时根据真实依赖关系重新排序。

如果任一 115 已经在共享环境执行：

```text
禁止简单重命名已执行 Migration。
```

应该：

```text
保留已执行版本
+
为另一组修改创建新的 Forward Migration
```

并核对：

```text
supabase_migrations.schema_migrations
```
