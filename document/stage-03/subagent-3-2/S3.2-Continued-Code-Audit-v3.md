# 17. 🟠 Messaging 幂等 Replay 状态返回有误导

如果第二个同键请求在第一个请求尚未完成时发现：

```text
delivery.status = queued
或
sending
```

当前 replay 逻辑仍可能构造：

```text
result.status = sent
```

因为只有：

```text
failed
```

被特殊处理，

其它状态统一按：

```text
sent
```

返回。

### 风险

Request A：

```text
Provider 仍在发送
```

Request B：

```text
已经告诉用户 sent
```

稍后 A 可能：

```text
failed
```

### 修复

Replay 必须映射真实状态：

```text
queued → queued
sending → queued/sending
sent → sent
delivered → delivered
failed → failed
```

不要把：

```text
not failed
```

等价于：

```text
sent。
```

# 18. 🟠 Frontend 网络结果不确定时仍会丢失原幂等键

页面：

```ts
pendingSendKey = crypto.randomUUID()

try {
  send()
}
catch {
}
finally {
  pendingSendKey = null
}
```

如果发生：

```text
请求超时
```

可能是：

```text
Server/Provider 已经发送成功
但浏览器没有收到响应。
```

`finally` 会：

```text
清空 Key
```

用户再次点击：

```text
生成新的 Idempotency-Key
```

于是服务器会认为：

```text
新的发送意图
```

并可能再次发送。

### 正确处理

仅在明确：

```text
成功
或
服务器明确返回业务失败且没有外部副作用
```

后清理 Key。

网络超时/连接中断：

```text
保留 Key
```

下一次重试继续：

```text
同一个 Idempotency-Key。
```

### 严重度

```text
P1/Pilot 前建议修
```

# 19. 🟡 Messaging `sending` 状态缺少故障恢复

```text

```


```text

```


```text

```

如果：

```text

```

```text
stale / retry
```

但在无法确定 Provider 是否已收到请求时：

```text
需要 Provider Idempotency / Message Key
```

共同保证。

```text
P1 Reliability
```

# 20. 🟡 附带发现：E2E Setup 新增 SQL 可能直接执行失败

本次包修改：

```text

```

新增：

```sql
insert into employee_role_assignments (...)
...

  tenant_id,
  employee_id,

  store_id

```

但当前 Schema 中：

```text

```

没有发现与这四列对应的：

```text

```


```text
there is no unique or exclusion constraint matching the ON CONFLICT specification
```

二选一：

```text

```

但要注意：

```text
store_id IS NULL
```

Tenant-wide Role 的 NULL 唯一语义。

或：

```text
B. E2E Setup 改成 INSERT ... WHERE NOT EXISTS
```

这是本轮附带发现。

不计入 S3.2 Feature Source Gate，但会影响后续 E2E Runtime。
