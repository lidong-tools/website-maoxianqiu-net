# 5. 🔴 Messaging P0 — 代码引用了不存在的 `message_deliveries.updated_at`

当前 `DeliveryRow` 声明：

```ts
updated_at: string
```

`isStaleSending()` 使用：

```ts
new Date(delivery.updated_at)
```

Retry CAS 过滤：

```text
updated_at.lt.<cutoff>
```

但是本次完整 97 个 Migration 中：

```text
没有任何 Migration
为 message_deliveries 增加 updated_at
```

初始表只有：

```text
created_at
```

Migration 112/115/118 也没有补：

```text
updated_at
```

### 影响

Retry 请求构造的 PostgREST Filter 会引用不存在列：

```text
message_deliveries.updated_at
```

因此存在直接数据库查询失败风险。

这不是类型提示问题，而是：

```text
Application Model
≠
Database Schema
```

### 必须修

推荐新增 Forward Migration：

```sql
alter table public.message_deliveries
  add column if not exists updated_at timestamptz not null default now();

create trigger ...
before update
execute procedure public.touch_updated_at();
```

或者：

```text
改 stale claim 使用真实存在、语义可靠的 claimed_at 字段。
```

更推荐显式：

```text
sending_claimed_at
```

因为它比通用 `updated_at` 更准确。

# 7. 重复发送竞态

```text

↓

↓
再次 Provider.send()
```

结果：

```text

可能产生两次外部消息。
```

```text

```

### 必须修

```text

↓ atomic

↓

```

# 8. 🔴 Messaging Frontend 状态模型没有 `sending`

数据库 Migration 118 已允许：

```text
sending
```

Backend `DeliveryStatus` 也使用：

```text
sending
```

但前端：

```ts
export type MessagingStatus =
  'queued' | 'sent' | 'delivered' | 'failed' | 'retry'
```

仍缺：

```text
sending
```

同时：

```ts
canRetry(row)
```

当前逻辑：

```text
只要不是 sent/delivered 且 attempts < 3
就显示 Retry
```

所以：

```text
queued
retry
failed
甚至 runtime 的 sending
```

都会被 UI 当成可重试。

### 修复

加入：

```ts
'sending'
```

并把 Retry 明确限制为：

```text
failed
retry
```

对于 stale sending：

```text
单独显示“发送结果未知”
```

不要作为普通 Retry 状态。

# 11. 🔴 Analytics P0 — Supabase many-to-one Relation 被错误当成 Array

退款表：

```text
refunds.invoice_id → invoices.id
refunds.payment_id → payments.id
```

对于从 `refunds` 查询父表：

```text
refund → invoice
refund → payment
```

这是 many-to-one 嵌套关系。

Supabase/PostgREST 对这种 Embedded Relation 返回：

```text
object | null
```

而不是：

```text
array
```

但当前 `revenue.ts` 手工断言成：

```ts
invoices?: { store_id: string | null }[]
payments?: { method: string | null }[]
```

并读取：

```ts
r.invoices?.[0]?.store_id
r.payments?.[0]?.method
```

---

# 12. 影响

实际嵌套对象类似：

```ts
invoices: {
  store_id: '...'
}
```

对对象执行：

```ts
invoices?.[0]
```

得到：

```text
undefined
```

所以：

### Refund Store

可能被错误归：

```text
unassigned
```

### Refund Payment Channel

可能被错误归：

```text
other
```

接口不会必然报错，

因此这是危险的：

```text
Silent BI Misclassification
```

---

# 13. 修复

不要继续手写错误 Result Cast。

至少改：

```ts
invoices?: {
  store_id: string | null
} | null

payments?: {
  method: string | null
} | null
```

读取：

```ts
r.invoices?.store_id
r.payments?.method
```

更推荐生成 Supabase Database Types 并使用：

```text
QueryData<typeof query>
```

让关系形状由数据库 Schema 推导。

# 17. 🟡 Analytics Timezone 仍有 DST 问题

当前日期转换仍以 Reference Time Offset 计算目标日期。

国际：

```text
America/New_York
Europe/London
```

等 DST 时区仍可能错 1 小时。

同时：

```text
local midnight + 86,400,000 ms
```

不适合 DST 切换日。

长期改成：

```text
Temporal / Luxon / date-fns-tz
```

并使用：

```text
[start, nextLocalMidnight)
```

半开区间。

中国 Pilot 风险低，国际化前必须处理。
