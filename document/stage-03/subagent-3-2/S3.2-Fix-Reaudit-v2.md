# 4. 🔴 Documents Sanitizer 仍有一个具体 Bug

当前：

```text
validateTemplateHtml()
```

会提取 `<style>` Block 并调用：

```text
validateStyleBlock(inner)
```

但是实现类似：

```ts
templateHtml = templateHtml.replace(
  STYLE_BLOCK_RE,
  (_full, inner) => {
    const problem = validateStyleBlock(inner)

    if (problem) {
      return problem
    }

    styleContent.push(inner)
    return ''
  }
)
```

问题：

```text
problem
```

只是被作为：

```text
replace 后的新字符串
```

塞回本地变量。

函数后续并不会：

```text
return problem
```

给调用方。

# 6. Documents 修复方式

不要用：

```text
replace callback return string
```

表示 Validation Failure。

应该：

```ts
let styleProblem: string | null = null

templateHtml.replace(
  STYLE_BLOCK_RE,
  (_full, inner) => {
    const problem = validateStyleBlock(inner)

    if (problem) {
      styleProblem = problem
    }

    return ''
  }
)

if (styleProblem) {
  return styleProblem
}
```

但长期仍推荐：

```text
HTML Parser
+
Tag Allowlist
+
Attribute Allowlist
+
URL Protocol Allowlist
+
CSS Allowlist
```

而不是依赖 Regex Sanitizer。

# 21. 🔴 Messaging Initial Send 仍可能重复发邮件

当前并发场景：

两个请求同时使用相同：

```text
Idempotency-Key
```

流程可能是：

```text
Request A：
查不到 Delivery

Request B：
也查不到 Delivery

A Insert
B Insert → unique conflict
```

B 的：

```text
createDeliveryRecord()
```

会回查并得到 A 创建的 Delivery。

问题在于：

```text
A
和
B
```

随后都继续：

```text
dispatchAndRecord()
```

所以：

```text
同一个 Delivery
```

仍可能调用 Provider 两次。

数据库的 Attempt Unique 即使阻止第二个 Attempt 记录，

也已经：

```text
无法撤回第二封邮件。
```

### 结论

```text
🔴 Initial Send Idempotency P0 尚未关闭
```

# 22. 🔴 Messaging Retry 也仍可能重复发送

当前 Retry：

```text
读取 attempts=1
↓
计算 next=2
↓
update delivery status=retry, attempts=2
↓
send
```

并发两个 Retry：

```text
A 读取 1
B 读取 1
```

A 更新：

```text
retry / 2
```

B 的条件仍可能匹配：

```text
status in queued/failed/retry
attempts < MAX
```

于是 B 也更新成：

```text
retry / 2
```

然后 A/B 都发送。

Again：

```text
Attempt unique
```

只能阻止数据库第二条记录，

不能阻止已经发生的 Provider Side Effect。

### 结论

```text
🔴 Retry Concurrency P0 尚未关闭
```

# 23. Messaging 正确 Claim 模型

需要真正 Compare-And-Swap。

例如：

```text
读取：
status=failed
attempts=1

UPDATE
WHERE id=?
AND status='failed'
AND attempts=1

SET:
status='sending'
attempts=2

RETURNING *
```

只有返回一行的 Request：

```text
才能调用 Provider。
```

另外 Initial Send：

```text
createDeliveryRecord
```

必须返回：

```ts
{
  delivery,
  created: boolean
}
```

只有：

```text
created=true
```

可以真正发送。

Idempotent Replay：

```text
created=false
```

只能返回已有状态，

不能再次 Provider Send。

# 24. 🔴 正常前端发送仍没有稳定 Idempotency Key

虽然 Backend 支持：

```text

X-Idempotency-Key
```

但当前 Messaging Frontend/API Client 并没有为用户每一次“发送动作”生成并持续复用一个 Key。

所以：

```text
双击发送

```

正常 UI 路径仍可能直接创建不同 Delivery。

### 修复

提交开始时：

```text
const key = crypto.randomUUID()
```

在该次发送完成/明确失败前：

```text
始终复用同一个 key。
```
