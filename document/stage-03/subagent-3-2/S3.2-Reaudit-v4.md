# 4. 🟠 chunk size=500 仍可能超过常见 URL 长度

一个 UUID 约：

```text
36 chars
```

500 个：

```text
约 18,000 chars
```

再加：

```text
逗号
括号
字段名
其它 query 参数
```

实际 URL 会更长。

不少代理/CDN/应用服务器常见限制约：

```text
8KB–16KB
```

因此：

```ts
chunk(ids, 500)
```

仍不能保证：

```text
不会 414 / URI Too Long
```

### 最低修复

建议：

```text
UUID chunk size = 100
```

或根据估算动态限制 URL 长度。

### 更成熟方案

这类：

```text
invoice items by invoice IDs
doctor by encounter IDs
```

最好继续下沉为：

```text
SQL JOIN / RPC
```

避免“先取 ID，再第二次 IN 查询”。

### 当前严重度

```text
P1 / Scale
```

如果 Pilot 数据量较小，不阻断小规模试点。





而不是长期依赖 Offset 拉全再 JS reduce。

```text

```

# 9. 🔴 Messaging 仍有一个遗漏的 replay 状态 Bug

文件已经新增统一函数：

```ts
replayResult(delivery)
```

它正确映射：

```text
queued   → queued
sending  → queued
retry    → queued
sent     → sent
delivered→ delivered
failed   → failed
```

但是 `sendMessage()` 最前面的快速查询分支仍然使用旧逻辑：

```ts
if (existing) {
  const result =
    delivery.status === 'failed'
      ? failed
      : sent
}
```

也就是说：

```text
Delivery = queued
或
Delivery = sending
```

如果新请求在最开头就命中 existing，

API 仍会返回：

```text
result.status = sent
```

# 10. 为什么需要修

场景：

```text
请求 A
已经创建 Delivery
正在 Provider Send

请求 B
同 Idempotency-Key
↓
顶部快速查询命中 Delivery(status=sending)
↓
API 返回 sent
```

但 A 后面可能：

```text
Provider Failed
```

B 已经提前告诉 UI：

```text
发送成功
```

### 修复非常小

把这一段旧逻辑替换为：

```ts
const result = replayResult(delivery)
```

与下面：

```text
created=false
```

分支统一。

### 当前严重度

```text
🔴 Messaging correctness blocker
```

# 12. 🟠 stale sending 恢复仍存在“外部结果未知”问题

新增：

```text
10 分钟后 sending 可被人工 Retry 回收
```

能避免：

```text
永久卡死
```

这是合理可靠性改进。

但是如果：

```text
Provider 已经成功发送
↓
应用进程在写数据库状态前崩溃
```

DB 会停在：

```text
sending
```

10 分钟后再次 Retry：

```text
可能发送第二次。
```

如果 Provider 本身没有：

```text
Idempotency Key / Message Deduplication
```

应用层无法完全确定第一次是否已经产生外部副作用。

### 更稳妥的产品语义

陈旧 `sending` 建议显示：

```text
发送结果未知
```

然后提供：

```text
查询 Provider 状态
```

如果 Provider 不支持查询：

```text
[重新发送]
```

需要明确提示：

```text
可能产生重复通知。
```

### 严重度

```text
P1 Reliability
```

不是当前普通并发 race。
