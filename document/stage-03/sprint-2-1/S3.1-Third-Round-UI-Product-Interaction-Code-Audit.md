# 2. 但当前还不能标记“UI / 交互完成”

本轮最重要的新结论：

> **当前主要问题已经从“布局结构不合理”转变成“UI 已经展示出成熟产品能力，但部分真实数据、权限、状态机和配置逻辑还没有跟上 UI”。**

这是比视觉问题更危险的一类问题。

典型：

```text
系统设置允许修改折扣审批阈值
↓
用户以为设置已经生效
↓
真正收费 RPC 仍固定按 10% 判断
```

以及：

```text
收银界面允许：
应收 ¥90
实收 ¥100
找零 ¥10

但 RPC：
amount > due
→ AMOUNT_EXCEEDS_DUE
```

这种问题会让用户产生：

> “界面看起来可以做，但实际提交失败”

因此本轮不建议继续先做大面积视觉精修。

建议先完成：

```text
UI 表达
=
真实业务逻辑
=
API
=
数据库规则
=
权限
```

的一致性收口。

# 5. P0-01：前端权限来源仍停留在 Legacy 模型

这是本轮发现的最高优先级问题之一。

文件：

```text
apps/maoxianqiu/src/store/modules/app/account.ts
```

当前路由生成调用：

```ts
appAccountStore.getPermissions()
```

而 `getPermissions()` 仍然只读取：

```text
store_members
→ roles.permissions
```

但是当前后端权限模型已经迁移到：

```text
employees
+
employee_role_assignments
+
role_permissions
```

平台管理员进一步改成：

```text
platform_user_roles
```

---

## 风险

后端可能判断：

```text
允许
```

但前端可能得到：

```text
permissions=[]
```

最终表现：

- 菜单消失；
- 按钮消失；
- 页面 404/无权限；
- 新 Tenant Owner 初始化后无法看到应该有的页面；
- 新 Employee Invite 后权限前后端不一致；
- Platform Admin 前端权限可能无法正确解析。

这属于：

> **UI 权限正确性 P0**

不是代码洁癖。

# 16. P0-09：System Settings 存在 Tenant Default 唯一约束缺陷

Migration：

```text
20260809000052_system_settings.sql
```

当前：

```sql
unique (
  tenant_id,
  store_id,
  namespace,
  key
)
```

但：

```text
store_id IS NULL
```

表示 Tenant Default。

PostgreSQL 默认 UNIQUE：

```text
NULL != NULL
```

因此可能出现：

```text
tenant A
store_id NULL
business / discount.threshold

多条记录同时存在
```

---

## 后果

Effective Settings：

```text
Map
```

最终使用哪一条 Tenant Default 可能变得不可预测。

# 17. 修复 System Settings 唯一性

Supabase 当前 PostgreSQL 版本支持时推荐：

```sql
UNIQUE NULLS NOT DISTINCT (
  tenant_id,
  store_id,
  namespace,
  key
)
```

升级 migration 要：

1. 先扫描重复 Tenant Default；
2. 保留最后更新时间最新的一条；
3. 删除重复；
4. 删除旧 Constraint；
5. 新建 `NULLS NOT DISTINCT` 唯一约束。

# 24. Cashier 金额模型应拆成两个概念

### Tendered Amount

客户实际递给收银员的钱：

```text
100
```

只用于现金找零。

### Applied Payment Amount

实际冲销发票的钱：

```text
90
```

因此：

```ts
change = tendered - due

paymentAmount = due
```

RPC：

```text
process_payment(amount=90)
```

---

## 非现金支付

微信 / 支付宝 / 银行卡：

通常：

```text
实收 = 应收
```

如果将来支持分次支付，再单独设计 Partial Payment。

不要让所有渠道都复用“现金递入金额”。
