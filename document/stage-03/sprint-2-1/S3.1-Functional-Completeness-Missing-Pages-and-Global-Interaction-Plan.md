# 1. 本文要解决的问题

当前系统经过 Stage-02 / Stage-03 后，已经存在大量业务页面与业务数据模型，但仍有三类产品完整性问题：

## A 类：功能底座已存在，但没有页面或没有入口

典型：

- `audit_logs` 已存在，但没有审计后台；
- `security_events` 已有 API，但没有安全事件页面；
- `approvals` 已存在，但没有统一审批待办；
- `payment_contexts` / `print_settings` 已存在，但没有配置维护界面。

## B 类：页面/入口存在，但只是模板或假功能

典型：

- “个人设置”入口存在，但“基本设置”直接显示“请开发者自行扩展”；
- 修改密码 UI 要求输入“原密码”，实际提交时原密码完全未参与验证；
- 登录页有“扫码登录”，但使用静态演示二维码，不是真实认证；
- 登录页开放“注册新帐号”，但当前产品 IAM 实际是“租户初始化 + 员工邀请”模式。

## C 类：功能有实现，但缺少跨页面的全局交互

典型：

- 已有 `currentTenantId/currentStoreId` Store，但没有实际门店切换组件；
- `setTenant()` / `setStore()` 在生产页面没有调用入口；
- 顶栏搜索只搜索导航菜单，不搜索客户/宠物/收费单/就诊号；
- 高风险审批散落在业务对象中，没有统一“我的待办”；
- 页面离开时没有统一未保存保护。

本轮工作的目标是：

> 把“很多业务模块已经能单独工作”的系统，补全成“用户从登录到跨模块工作都连续、可理解、可恢复”的产品。

# 3. 修改密码当前逻辑不成立

当前修改密码表单要求：

```text
原密码
新密码
确认密码
```

但 Store 中实际实现：

```ts
supabase.auth.updateUser({ password: data.newPassword })
```

`password`（原密码）完全没有参与认证。

同时 UI Toast：

```text
模拟修改成功，请重新登录
```

这显然不是正式产品行为。

## 正确设计

修改密码应：

```text
输入当前密码
↓
重新认证当前用户
↓
认证成功
↓
修改新密码
↓
退出其他/当前会话（按产品策略）
↓
重新登录
```

可以使用 Supabase Auth：

1. 当前账号 email；
2. `signInWithPassword({ email, password: oldPassword })` 进行 re-auth；
3. re-auth 成功后再 `updateUser({ password: newPassword })`。

不得：

- 把原密码写数据库；
- 把原密码写日志；
- 前端仅做字符串校验就修改密码。

# 4. 找回密码流程未闭环

当前：

```text
登录页
↓
输入邮箱
↓
resetPasswordForEmail()
↓
提示“去邮箱完成”
```

但是当前路由中没有专门处理 Password Recovery Session 的正式页面。

必须补：

```text
/auth/reset-password
```

流程：

```text
点击邮件重置链接
↓
Supabase 恢复 recovery session
↓
显示“设置新密码”
↓
确认
↓
updateUser
↓
成功
↓
返回登录页
```

需要处理：

- 链接过期；
- token 无效；
- 已使用；
- 两次密码不一致；
- 密码强度；
- 成功后 session 清理。

# 6. “注册新帐号”与当前 SaaS IAM 冲突

当前系统真正的员工进入路径是：

```text
租户初始化
+
管理员邀请员工
+
employee
+
store assignment
+
role assignment
```

而登录页的注册是：

```text
supabase.auth.signUp()
```

注册完成后：

- 不自动创建 tenant；
- 不自动创建 employee；
- 不自动分配 store；
- 不自动分配 role。

因此可能产生：

```text
Auth 用户存在
但没有业务身份
```

的孤儿账号。

## Pilot 正确策略

### 推荐方案

B2B Pilot：

```text
关闭公开注册
```

登录页改为：

```text
账号登录
忘记密码
```

并显示：

```text
没有账号？请联系医院管理员邀请。
```

### 后续如果要自助 SaaS 注册

必须建立完整：

```text
注册
→ 邮箱验证
→ 创建医院
→ Tenant 初始化
→ 首店
→ Owner
→ 进入系统
```

不能只恢复 `signUp()` 按钮。

# 7. 登录页远程演示图片需要移除

当前登录页引用远程生成图片 URL。

正式系统不得依赖第三方演示图服务作为核心登录页资源。

处理：

- 转成本地静态资源；
- 或使用系统 R2/CDN 的正式品牌资源。

避免：

- 第三方失效；
- 加载不稳定；
- 隐私/请求泄漏；
- 登录页首屏不可控。

# 11. 当前上下文存储也需要修正

现在 key：

```text
currentTenantId
currentStoreId
```

是浏览器全局 key。

如果同一台电脑不同账号登录：

```text
用户 A 的门店上下文
```

可能残留给：

```text
用户 B
```

虽然服务端权限仍应阻止越权，但 UX 和数据筛选会错乱。

改为至少：

```text
mxq:{userId}:tenant
mxq:{userId}:store
```

或者登录 session store。

并且：

```text
logoutCleanStatus()
```

必须同时：

```text
appTenantStore.clear()
```

当前 logout 清理流程没有清除 Tenant Store。

# 15. Global Search API

新增：

```http
GET /api/search?q=&storeId=&limit=
```

返回：

```ts
{
  customers: [],
  pets: [],
  encounters: [],
  invoices: [],
  catalogItems: []
}
```

必须：

```text
先权限过滤
后返回结果
```

不能：

```text
浏览器下载多个完整表
↓
前端搜索
```

### 搜索策略

第一版 PostgreSQL：

- `ILIKE`
- 已有业务索引；
- 每类最多返回 5–10 条。

后续数据量大再考虑：

- pg_trgm；
- FTS；
- 专用 Search Service。

### 数据库

第一版不强制新增搜索表。

如果性能验证发现需要：

```sql
create extension if not exists pg_trgm;
```

并增加合适的 trigram index。

不要第一版就引入 Elasticsearch。

# 24. PRD 的敏感审批目前只实现了一部分

PRD 要求：

- 高额退款；
- 高额库存调整；
- 跨店调拨审核；
- 病历特殊修改；
- 权限变更；
- 租户停用/恢复。

并要求：

```text
阈值可配置
申请人 ≠ 审核人
```

当前真实代码中最明确落地的是：

```text
发票折扣 > 10%
```

而且 `10%` 直接硬编码在 billing migration / UI 中。

`process_refund` 当前直接退款，没有按金额生成审批。

所以：

> “审批中心 UI”不能掩盖“审批规则底层尚未完整实现”。

