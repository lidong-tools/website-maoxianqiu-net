# 2. 当前 UI 的系统性问题

## 2.1 43 个业务页面隐藏了 PageHeader

当前大量页面写法：

```vue
<FaPageHeader :show="false" ... />
```

而 `packages/components/src/basic/page-header/index.vue` 中：

```vue
<div v-if="show !== false">
```

意味着：

> `show=false` 并不是“缩小标题”，而是整个标题栏完全不渲染。

因此大量页面缺失：

- 页面标题；
- 页面说明；
- 页面级主操作；
- 当前实体/业务状态；
- 用户进入页面后的第一视觉层级。

### 改造原则

不能简单把所有 `show=false` 改成 `true`。

应该新增统一业务标题容器，例如：

```text
BusinessPageHeader
```

结构：

```text
标题 + 简短业务说明/状态
                       主操作
                       次操作
```

高频工作台页面标题高度应控制在约 56–72px，不使用过厚 Header。

# 3. `FaPageMain` 嵌套卡片过多

当前 `FaPageMain` 本身已经带：

- `m-4`
- `rounded-lg`
- `border`
- `bg-card`
- `p-4`

很多业务页面内部继续使用：

```text
FaPageMain
 └ Card
    └ Card / border block
```

造成：

- 页面像“卡片套卡片”；
- 信息层级不清；
- 实际内容宽度变窄；
- 高密度医疗业务页面浪费横向空间。

### 改造原则

以后业务页面按三种容器处理：

### A. 数据列表页

```text
Page
├ Header
├ FilterBar
└ Table
```

列表表格不再额外包多层 Card。

### B. 详情页

```text
Page
├ EntitySummaryHeader
├ KeySummary
└ Tabs
```

### C. 工作台/复杂业务页

```text
Page
├ Context Header
├ Split Workspace
└ Fixed Action Bar
```

不使用普通表单页的卡片堆叠方式。

# 4. 搜索区普遍过重

当前很多页面统一使用：

```vue
<FaSearchBar :show-toggle="false">
  <div class="grid grid-cols-[repeat(auto-fit,minmax(300px,1fr))]">
```

问题：

- 两三个简单筛选条件也占一整块大区域；
- 300px 最小列宽导致 1280–1440 下容易换行；
- 列表正文被压低；
- “搜索/筛选”和业务内容权重倒置。

## 统一改造

新增：

```text
BusinessFilterBar
```

第一行只保留：

- 高频搜索；
- 1–3 个核心筛选；
- 查询/重置；
- 高级筛选按钮。

次要条件放高级区域折叠。

---

# 5. 表格操作列按钮过多

大量页面目前：

```text
查看 | 编辑 | 状态切换 | 删除 | 其他动作
```

全部直接平铺。

改造为：

```text
主下一步动作 + 更多(...)
```

例如：

```text
预约：
[签到] [...]
```

更多菜单：

```text
编辑
取消
查看详情
```

这样降低视觉噪声，并突出真正的下一步业务动作。

---

# 6. 列表中大量显示原始 ID

源码中频繁存在：

```text
客户 ID
宠物 ID
商品 ID
业务 ID
Admission ID
```

对于医院员工，这些不是有效工作信息。

UI 应优先显示：

```text
宠物名
主人名
手机号
医生名
床位
单据号
商品名 / SKU
```

ID 只放在：

- 详情；
- Tooltip；
- 调试；
- 二级信息中。

这类优化通常需要 **API Query enrichment**，但不需要改数据库表。

---

# 7. 复杂流程没有使用 FixedBar

PRD/UI 规范已经明确存在：

```text
FaFixedBar
```

但生产业务页面几乎没有使用。

必须优先用于：

- 病历编辑；
- 收银；
- 盘点；
- 调拨；
- 入院；
- 出院结算；
- 租户初始化；
- 大型审批/签署流程。

固定栏中放：

```text
左：状态/金额/校验结果
右：保存草稿 / 主提交动作
```

```text

```

仅两栏。

这与 PRD 明确的三栏工作台不一致。

## 目标布局

```text
┌───────────────────────────────────────────────────────────────┐
│ 毛球 | 英短 | 3岁 | 5.2kg | ⚠青霉素过敏 | ⚠易应激          │
├─────────────┬─────────────────────────────┬─────────────────┤
│ 候诊/历史    │ 病历编辑                    │ 医疗操作        │
│ 260–300px   │ flexible                    │ 340–380px       │
│             │ 主诉                        │ 处方            │
│ 今日队列     │ 现病史                      │ 检验            │
│ 最近就诊     │ 体格检查                    │ 医嘱/处置       │
│             │ 诊断                        │                 │
├─────────────┴─────────────────────────────┴─────────────────┤
│ 自动保存 10:23                    [保存草稿] [完成] [签署]   │
└───────────────────────────────────────────────────────────────┘
```

使用：

```text
FaFixedBar
```

### 重要 UI 规则

- 病历编辑区永远是最大区域；
- 宠物风险固定可见；
- 处方/检验不应弹多个 Modal 打断医生；
- 右侧通过 tabs/accordion 切换；
- 最近历史在左栏快速查看；
- 保存状态必须可见。

### API

建议：

```http
GET /api/clinical/encounters/:id/workbench
```

一次加载：

- pet/customer summary；
- recent records；
- encounter；
- prescriptions；
- medical orders；
- lab orders。

### DB

**建议增加乐观锁：**

```sql
version integer not null default 1
```

病历保存：

```text
expectedVersion
```

冲突返回：

```http
409 Conflict
```

避免多窗口/多终端覆盖病历。

属于推荐的 P0 数据一致性改造。

# 59. API 改造执行原则

ds 必须遵守：

### Query

读取/聚合可以：

```text
Frontend → Query/Hono → DB
```

复杂详情和工作台优先 Hono 聚合。

### Command

医疗、收费、库存、权限等写操作：

```text
Frontend
↓
Hono Command
↓
RPC / Transaction
↓
DB
```

不得因为 UI 重构重新引入前端直写关键表。

# 60. 禁止事项

本次 UI 改造禁止：

1. 修改现有导航分组作为“优化成果”；
2. 大面积更换颜色/圆角却不解决工作流；
3. 为了“高级感”降低医疗信息密度；
4. 每个 section 都套 Card；
5. 把复杂操作全部塞 Modal；
6. 用原始 UUID 代替业务名称；
7. 因为一个页面需要组合展示就随意建新表；
8. 重写已有业务 Command/RPC 而不理解现有事务；
9. 只做静态页面，不接现有真实数据；
10. 未验证 1280 / 1440 / 1920 桌面布局就标记完成。

# 61. 最终目标

这轮 UI 改造不是把毛线球“做得更漂亮”。

真正目标是：

```text
前台：
更快找到客户、宠物、预约、收费

医生：
在一个工作台完成病历、处方、检验、医嘱

护士：
按时间和患者执行任务，而不是浏览数据库表

检验：
按标本和流程状态工作

住院：
围绕患者/床位/任务工作

库管：
按库存单据工作

财务：
在金额上下文完整的情况下收银、日结、对账

管理员：
以业务对象和风险状态管理系统
```

最终页面应该呈现出成熟宠物医院 SaaS 的工作台感，而不是“后台管理系统 CRUD 页”的感觉。
