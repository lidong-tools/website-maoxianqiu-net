### R-3 3.4.2.3-08 登录提醒：安全事件写入链路缺失（判定：不完整实现）

- **现状**：`security_events` 表已建（`20260806000018_operations.sql` L277-294：event_type/severity 枚举+索引），安全事件查询页面已落地（`apps/maoxianqiu/src/views/system/audit/index.vue` 安全事件 Tab，L409-546；前端类型映射含 login_failed/permission_denied/suspicious/data_export L194-199），查询 API 在 `api/routes/operations.ts` L1001-1027（注释"仅 service_role 写入"）。但**全库无任何 security_events insert**（无登录成功/失败/敏感操作写入逻辑，无触发器/写入路由），安全事件页面为空转；登录提醒开关与"发送到院长手机"触发链路不存在（SETTING_REGISTRY 无安全通知键，`api/routes/settings.ts` L29-35 仅 5 个 business 键）；短信渠道 `api/providers/sms.ts` 为通用 HTTP JSON 抽象（L20-60），依赖 MESSAGING_SMS_API_URL/KEY/SIGN 环境变量。
- **修复内容**：
  1. **新增写入通道**：在 `api/routes/operations.ts` 新增 `POST /operations/security-events`（service_role 权限，校验 event_type/severity 枚举后 insert）或 Supabase Auth 登录事件触发器；优先采用 Hono 路由方案便于审计与权限控制。
  2. **认证链路埋点**：登录失败（登录页 `signInWithPassword` 失败回调）→ 写 `login_failed`；登录成功（新设备/异地可选）→ 写 `login_success`；权限拒绝（`api/lib/permission.ts` `requireScopedPermission` 抛错分支）→ 写 `permission_denied`。前端登录为 Supabase Auth 直连（无后端 /auth/login 路由），需在登录页/auth composable 失败回调处调用写入 API。
  3. **登录提醒开关与通知**：SETTING_REGISTRY 增加安全通知键（如 `security.login_alert.enabled` / `security.alert.phone`），系统设置页补充对应配置 UI（可在现有业务规则 Tab 或新增 Tab）；当开关开启且短信渠道已配置（环境变量存在）时，写入事件后调用 `api/providers/sms.ts` 发送到配置手机号；未配置渠道时仅落库不报错（维持现有 PROVIDER_NOT_CONFIGURED 语义，不 mock 伪造投递）。
- **涉及位置**：
  - `api/routes/operations.ts`（L1001-1027 附近新增写入路由）
  - 登录页 / auth composable（`apps/maoxianqiu/src/views/login/` 或 `apps/maoxianqiu/src/stores/auth.ts` 等，失败/成功回调埋点）
  - `api/lib/permission.ts`（权限拒绝分流写事件，可选）
  - `api/routes/settings.ts` L29-44（SETTING_REGISTRY + BUSINESS_RULE_DEFS 增加安全通知键）
  - `apps/maoxianqiu/src/views/system/settings/index.vue`（配置 UI）
  - 复用 `api/providers/sms.ts`、`api/lib/audit.ts`（apiAudit.listSecurityEvents 已有）
- **优先级**：P0（安全事件功能空转，审计与安全通知的核心写入缺失）
- **验证方式**：用错误密码登录一次 → 安全事件 Tab 出现 `login_failed` 记录（含时间/租户/账号）；越权操作触发权限拒绝 → `permission_denied` 落库；配置 `security.login_alert.enabled=true` + 有效短信渠道后，登录事件触发短信（依赖环境变量，未配置时仅落库）。

### R-4 3.4.2.3-07 积分：消费积分获得规则未接入收费（判定：不完整实现）

- **现状**：积分账户/不可变流水/手工调整完整（`point_transactions` 表 `20260806000018_operations.sql` L97-109 reason 枚举 purchase/redeem/adjust/expiry、L359-372 仅 insert 策略=不可变；`adjust_points` RPC L665-784 含幂等/审计；会员中心积分流水 Tab `apps/maoxianqiu/src/views/operations/memberships/index.vue` L587-610；等级积分倍率维护 L46-54）。但 `membership_tiers.points_multiplier` **仅存储未参与消费计算**：`api/routes/billing.ts` L287-300 调 `create_invoice` RPC 仅传 `p_apply_membership_discount`，无积分参数；`create_invoice`（`20260810000057_membership_billing_integration.sql`）无积分计算；PRD §27.1.2 的消费积分比例/充值积分/退款回退/积分抵扣上限等参数不在 SETTING_REGISTRY（`settings.ts` L29-35 仅 5 个 business 键）。
- **修复内容**：
  1. **收费积分计算**：在 `create_invoice` RPC（`20260810000057_membership_billing_integration.sql`）内新增积分获得逻辑——按客户有效会员等级 `points_multiplier` × 可积分金额（实收金额，可排除抵扣部分，规则待产品确认）计算应得积分，事务内写 `point_transactions`（reason=purchase）+ 更新积分余额，以 invoice_id 幂等防重复积分。
  2. **退款回退**：退款/发票作废流程中按原发票积分扣回（reason=adjust 或新增 reason，事务内处理，防负数）。
  3. **积分参数入库**：SETTING_REGISTRY 增加积分命名空间键（如 `points.earn.ratio`、`points.redeem.enabled`、`points.redeem.max_per_invoice`、`points.validity_days`、`points.recharge.earn`、`points.refund.revoke`），`settings.ts` BUSINESS_RULE_DEFS 同步定义默认值，设置页（业务规则 Tab 或新 Tab）可维护。
- **涉及位置**：
  - `supabase/migrations/20260810000057_membership_billing_integration.sql`（create_invoice RPC 增积分逻辑，需新增迁移而非改旧迁移）
  - `api/routes/billing.ts`（L287-300 调用参数，若积分入参需扩展）
  - `api/routes/settings.ts`（L29-44 SETTING_REGISTRY + 默认值）
  - `apps/maoxianqiu/src/views/system/settings/index.vue`（积分参数 UI）
- **优先级**：P1（业务闭环缺口，涉及收费金额计算需谨慎回归）
- **验证方式**：为某会员等级设置 points_multiplier=2，创建该客户发票并收款后，`point_transactions` 出现 reason=purchase 记录、余额按倍率增加；同一发票重复提交不重复积分；退款后积分回退；积分参数在设置页可配置并影响计算。

### R-7 3.4.3.2-01 主观诊断设置：全库无实现（判定：未实现）

- **现状**：全前端无"主观诊断/医生模板"维护页面（检索"主观/主观诊断/医生模板"无命中），无对应数据表/RPC（migrations 无 subjective_diagnosis / doctor_template 相关表），医生工作台诊断输入辅助为硬编码（同 R-2 的 `QUICK_DIAGNOSES`）。PRD §31.3 定义为"主观判断模板——作为医生输入辅助，不应自动作为正式诊断"。
- **修复内容**（二选一，需产品确认）：
  - **方案 A（实现）**：
    1. 新增数据表（如 `doctor_templates`：tenant_id/category/subcategory/content/sort_order/is_active，(tenant_id,code) 唯一），可并入现有迁移体系。
    2. 在统一目录页 `apps/maoxianqiu/src/views/catalog/index.vue` 新增"主观诊断模板"维护区（根类目/子类目增删改 + 诊断内容维护），CRUD API 参照 `api/routes/catalog.ts` 中 intake-questions/diagnosis-dict 模式（带审计）。
    3. EncounterEditor 诊断区接入模板数据源（与 R-2 共用快捷项数据加载机制），点击仅插入输入框文本、不自动作为正式诊断。
  - **方案 B（延期）**：在映射矩阵标注"延后"（同设备接入/钱箱处理），医生工作台暂以 R-2 诊断字典快捷项覆盖录入辅助，手册对照时备注理由。
- **涉及位置**：
  - 方案 A：新增 `supabase/migrations/` 迁移、`apps/maoxianqiu/src/views/catalog/index.vue`（新增 Tab/分区）、`api/routes/catalog.ts`（新增 CRUD）、`EncounterEditor.vue`（数据源接入）
  - 方案 B：仅更新映射矩阵/需求文档
- **优先级**：P2（PRD 定位为医生输入辅助，非核心闭环；与 R-2 联动实施更省成本）
- **验证方式**：方案 A——维护界面增删改根类目/子类目/内容后，医生工作台快捷项联动；快捷项插入的文本不会出现在正式诊断结构化字段中。方案 B——文档标注延期理由即可。
