## 一、真实缺口（需修复）

### R-1 3.6.2-02 住院/寄养自动计费规则（判定：不完整实现）

- **现状**：PRD §33 规划的 `inpatient_charge_rules` / `inpatient_charge_periods` 计费规则表在整个 `supabase/migrations` 目录中不存在（全库 grep 无任何命中）。当前住院日费由 `generate_daily_charges(date)` RPC 按 `cages.daily_rate` 手动/按需触发（migration 21 L1033-1091，幂等键 admission_id+charge_date+catalog_item_id），寄养基础房费在离店时由 `boarding_prepare_checkout` 一次性计入 Invoice（migration 73 L123-177 / migration 91）。无"按房间类型关联默认收费项目、具体笼位可覆盖、价格快照、换房分段计费、暂离不释放房位、日切规则（自然日零点/固定营业日切/不足一日/延迟出院宽限）"能力；无独立自动计费任务调度（全库无 pg_cron/pgagent/pg_timetable 使用）。
- **修复内容**：
  1. 新增迁移：建 `inpatient_charge_rules`（name、catalog_item_id、billing_unit、cutoff_time、grace_minutes、status、room_type 关联默认项目 + cage_id 可覆盖、价格快照列）与 `inpatient_charge_periods`（period_start/end、invoice_line_id、idempotency_key）两张表，幂等键 (admission_id, catalog_item_id, billing_period)；
  2. 新增自动计费 RPC（如 `run_daily_billing`）：按日切规则对在住/在养记录逐日生成费用，落 `inpatient_charges` / `boarding_service_charges`，幂等防重；
  3. 落地定时调度：优先用 Supabase pg_cron（`cron.schedule`）每日日切执行；若平台未启用 pg_cron，则在 Hono API 侧提供定时任务入口 + 前端"执行日切计费"按钮兜底；
  4. 换房分段计费：`transfer_cage` / `boarding_change_cage` 时对当前 period 做截断，新 cage 按新规则/新价格快照续算；
  5. 寄养基础房费改为逐日自动计费（而非仅离店一次性入账），`boarding_prepare_checkout` 复用 periods 汇总。
- **涉及位置**：
  - 新增：`supabase/migrations/<新迁移>_inpatient_charge_rules_periods.sql`（建表 + 计费 RPC + cron 调度）
  - 改动：`api/routes/inpatient.ts`（计费规则 CRUD + 日切触发接口，L899+ 寄养区附近）、`apps/maoxianqiu/src/api/modules/inpatient.ts`、`apps/maoxianqiu/src/types/inpatient.ts`（新增 ChargeRule / ChargePeriod 类型）
  - 参考：migration 21 L1033-1091（现有 generate_daily_charges 可改造复用）、migration 73 L123-177（boarding_prepare_checkout）
- **优先级**：P0（核心业务闭环缺失——自动计费是 PRD §33 明确规划项，3.6.2-02 判定"不完整实现"的主要差距；当前住院日费依赖人工触发、寄养房费离店才出账，无法支撑 KPI 口径的住院/寄养收入逐日归集）
- **验证方式**：① 新迁移在空库/升级库可成功执行，`inpatient_charge_rules`/`inpatient_charge_periods` 表存在且有 RLS 与幂等约束；② 模拟住院 2 天 + 换 1 次笼位：日切调度后 `inpatient_charges` 按天生成 3 段费用、无重复行（幂等键生效）、换房前后费率分别取对应笼位价格快照；③ 寄养入住后未离店，日切后 `boarding_service_charges` 已含逐日房费；④ 重复执行同一日切任务费用行数不增；⑤ 前端结算页/寄养详情能展示按周期拆分的费用明细。

### R-2 3.6.2-01 住院/寄养费用类目 billing_type 专用类型缺失（判定：不完整实现）

- **现状**：`catalog_items.billing_type` check 仅 `('service', 'product', 'drug', 'vaccine', 'exam')`（migration 16 L57-61），PRD §14.1 规划的 `hospitalization` / `boarding` 专用类型未落地；住院/寄养收费项目当前只能归入通用 'service' 类目，无法在类目语义上区分"住院床位费/寄养服务费"（PRD §33 L767 明确 hospitalization/boarding 分别对应住院床位费和寄养服务费），与 R-1 计费规则表（按 room_type 关联默认收费项目）落地后也需要用专用类型做归集。
- **修复内容**：
  1. 新迁移：drop 旧 `catalog_items_billing_type_check` 并重建为含 `'hospitalization'`、`'boarding'` 的 check；存量数据不受影响（默认 service 仍合法）；
  2. 前端 Catalog 模块：`apps/maoxianqiu/src/views/catalog/components/CatalogItemForm.vue` 的 billing_type 下拉补充"住院费/寄养费"选项；
  3. 类型同步：前端 `apps/maoxianqiu/src/types/` 中 catalog 相关 BillingType 类型补 `'hospitalization' | 'boarding'`；`api/routes/` catalog 相关 schema 校验同步放开；
  4. 可选：在 R-1 落地时要求住院/寄养自动计费仅允许引用 billing_type ∈ (service, hospitalization, boarding) 的目录项。
- **涉及位置**：
  - 新增：`supabase/migrations/<新迁移>_catalog_billing_type_extend.sql`
  - 改动：`apps/maoxianqiu/src/views/catalog/components/CatalogItemForm.vue`、catalog 类型定义文件、catalog API schema（`api/routes/` 下 catalog 路由）
  - 参考：migration 16 L57-61（原 check）、migration 70 L12-15（同类"drop+重建 check"写法）
- **优先级**：P1（重要语义/体验缺失——3.6.2-01 判定"不完整实现"；虽不阻塞现有 service 类目计费，但类目无法表达住院/寄养专用语义，且是 R-1 计费规则按类型归集的先决条件）
- **验证方式**：① 新迁移执行后 `catalog_items_billing_type_check` 含 hospitalization/boarding；② 通过 Catalog 页面可新增 billing_type=hospitalization/boarding 的项目并挂门店价格；③ 住院/寄养自动计费生成的费用行能通过 billing_type 归集到对应 KPI 口径（inpatient_charges / boarding_service_charges）。

### R-3 3.6.1-01 前端 RoomType 类型未含 boarding（判定：已实现，次要缺口需顺手修复）

- **现状**：DB 侧已支持——migration 70 L12-15 将 `rooms_room_type_check` 扩展为含 `'boarding'`；但前端 `apps/maoxianqiu/src/types/inpatient.ts` L8 `RoomType = 'ward' | 'icu' | 'isolation' | 'standard'` 未含 'boarding'，L496-501 `ROOM_TYPE_LABELS` 无 boarding 映射，导致 `views/inpatient/facility/index.vue` L443-447 房间类型下拉（`Object.entries(ROOM_TYPE_LABELS)`）**无法选择"寄养房"类型**——用户无法通过 UI 创建寄养房，只能靠 DB 直插；寄养办理入住走 `boarding_cage_status` 视图（migration 73 L288-317）选择可用笼位，业务闭环不受阻。
- **修复内容**：
  1. `types/inpatient.ts` L8：`RoomType` 联合类型增加 `'boarding'`；
  2. L496-501：`ROOM_TYPE_LABELS` 增加 `boarding: '寄养房'`；
  3. 全量检查 `apps/maoxianqiu/src` 中 `RoomType` 使用处（如房态看板 `views/inpatient/dashboard`、facility 表单校验、类型下拉、颜色/图标映射）是否需补 boarding 分支，确保类型安全（TS 编译无遗漏）；
  4. 前端 types 修正后确认 `facility` 页可新增/编辑寄养房，且寄养房下的笼位仍可被 `boarding_cage_status` 视图正常读取。
- **涉及位置**：
  - 改动：`apps/maoxianqiu/src/types/inpatient.ts`（L8、L496-501）、`apps/maoxianqiu/src/views/inpatient/facility/index.vue`（下拉展示，类型修正后自动生效）、`apps/maoxianqiu/src/views/inpatient/dashboard/index.vue`（如存在按 RoomType 分组/过滤逻辑）
  - 参考：migration 70 L12-15（DB 已含 boarding，前端对齐即可）
- **优先级**：P1（重要体验缺失——3.6.1 需求"添加房间时选择类型（住院/寄养）"的 UI 交互缺失一半：无法在设置页创建寄养房；修复成本极低，纯前端类型补全）
- **验证方式**：① `tsc`/`vue-tsc` 类型检查通过；② facility 页面新增房间弹窗类型下拉可见并可选"寄养房"，保存后 `rooms.room_type='boarding'` 落库；③ 新建寄养房下的笼位在寄养房态视图（boarding_cage_status）中正常展示并可办理入住。

## 二、产品决策项（无需修复或需确认）

1. **寄养任务未并入 workflow_tasks 护士工作台页签**（3.7.3-01，检查判定✅已实现）：寄养以独立 Boarding Domain 形态落地——独立页面 `/inpatient/boarding`（路由 L98-105）+ 独立权限码 boarding.view/manage/care/checkout（migration 70 L32-39，护士持 boarding.view+care），寄养每日照护在寄养详情 Drawer 操作，未生成 workflow_tasks 类型的"寄养页签"。此形态符合 Agent-06"寄养独立 Boarding Domain、权限与医疗住院分离"规划，功能等价满足竞品"寄养页签指引至住院寄养模块"描述 → **无需修复**，如需与护士工作台页签统一，需产品确认（是否将寄养每日照护/待办并入护士工作台）。
2. **统一服务目录多级类目替代"住院/寄养专属费用窗体"**（3.6.2-01/3.6.2-02 形态差异）：毛线球为"升级形态"，以 catalog 三级类目树（migration 290）承载住院/寄养收费项目，住院费用落 inpatient_charges、寄养费用落 boarding_service_charges（KPI L34-35 已定义），功能上覆盖竞品"费用窗体 + 类目/子类目 + 收费项目增删改" → **产品决策已定，无需修复**（类目语义缺 hospitalization/boarding 专用类型见 R-2，属真实缺口）。
3. **寄养/住院笼位单占用互斥策略**（cages_single_occupancy_check，migration 70 L22-25）：住院与寄养不可同时占用同一笼位，且笼位状态"占用中"禁止人工切换（facility L239-250）→ 符合并发安全要求，无需修复。
