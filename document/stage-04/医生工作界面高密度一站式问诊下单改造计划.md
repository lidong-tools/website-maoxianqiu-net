# 医生工作界面高密度一站式问诊下单改造计划

> 目标页面：`/clinical/workbench`（路由标题“医生工作”）  
> 目标应用：`apps/maoxianqiu`  
> 计划性质：基于 2026-08-10 当前代码的实施计划，不包含本轮代码改造  
> 优先级：P0，建议作为 Stage-04 后续体验收口任务执行

## 1. 改造目标

将当前“队列 + 纵向病历 + 只读医疗操作摘要”改造成医生可在同一患者上下文中连续完成以下工作的高密度工作区：

1. 识别候诊患者并叫号、开始接诊；
2. 查看分诊、过敏、风险、主人及宠物核心信息；
3. 录入主诉、病史、检查、诊断、治疗方案和复诊安排；
4. 开具处方、检验、影像和治疗/护理医嘱；
5. 在当前界面核对项目、费用、执行去向及阻断风险；
6. 保存草稿、提交诊疗方案、结束问诊，不因跨页面跳转丢失上下文。

### 1.1 可量化目标

| 指标 | 当前状态 | 改造目标 |
|---|---|---|
| 完成一次“接诊 → 病历 → 多类下单 → 提交”所需页面 | 至少涉及工作台、病历详情、检验/影像或医嘱页 | 常规流程 1 个页面完成 |
| 医疗操作入口 | 多数为“管理/查看/跳转”，脚本中的快捷入口不可达 | 处方、检验、影像、医嘱均在右侧工作区可直接新增与编辑 |
| 1280 宽度可用性 | 固定 `280 + auto + 360`，中间区易被挤压 | 病历正文始终保留可编辑宽度，左右区域按内容宽度折叠 |
| 首屏信息密度 | 病历字段单列纵向堆叠，滚动距离长 | 常用字段分组、双列/紧凑布局，核心状态与动作首屏可见 |
| 数据加载 | 浏览器并发拼装预约、客户、宠物、病历、处方、检验 | 候诊队列与患者工作区均消费服务端业务 DTO |
| 关键命令 | 分散提交，缺统一诊疗方案提交边界 | 每个命令幂等；批量提交方案时支持单事务或明确的失败恢复 |
| E2E | 只覆盖病历保存/完成，且断言与当前模板行为有偏差 | 覆盖真实问诊、四类下单、计费、任务、事件与防重复 |

### 2.2 P0 问题

#### P0-1：已经编写的快捷下单能力在模板中不可达

页面脚本存在 `openPrescription`、`openDiagnostic`、`onCreateDiagnosticOrder`、`onCallPatient`、`onStartConsultation` 和 `queueCounts`，但模板没有绑定这些函数，也没有处方/检查编辑器。当前右栏只有：

- 处方“管理”跳转病历详情；
- 检验“查看”跳转检验工作台；
- 影像“申请”跳转影像工作台；
- 完全没有“开立医嘱”入口。

这正是“不能一个界面快速完成问诊和下单”的直接原因。改造时不能只调整间距，必须把下单编辑能力真正接入模板。

#### P0-2：存在两套医生工作台数据模型

当前医生页面同时使用：

- `listAppointments + Supabase pets/customers + listEncounters + listPrescriptions + listLabOrders`；
- Stage-04 新增的 `GET /workbenches/doctor`；
- 但没有使用已存在的 `GET /clinical/encounters/:id/workspace`。

结果是浏览器负责跨表拼装、请求数量多、队列状态来自预约和患者旅程两套来源，且与 `document/stage-04/多岗位协同门诊患者旅程.md` 中“岗位工作台只消费服务端聚合结果”的约束不一致。

#### P0-3：固定列宽压缩病历正文

当前内容区为 `p-4`、列间距 `gap-4`、左栏 280px、右栏 360px。加上应用侧边栏后，1280 宽度下病历区会明显不足；字段仍是单列纵向排列，滚动成本高。

#### P0-4：患者临床上下文不完整

页面虽然显示 `PetSafetyBanner`，但缺少始终可见的：

- 主人姓名与联系方式；
- 宠物品种、性别、年龄、当前体重；
- 分诊等级、体温、心率、呼吸、疼痛评分；
- 过敏、慢病、既往诊断、当前用药；
- 本次就诊阶段、未付金额、下游阻断项。

医生需要在不同页面或卡片中寻找信息，不利于快速判断和安全下单。

#### P0-5：问诊录入仍是“长表单”

主诉、现病史、检查发现、诊断、治疗方案、复诊日期全部单列排列，且多行内容使用 `FaInput type="textarea"`。没有：

- 问诊问题库快捷插入；
- 常用诊断/病历模板；
- 键盘保存；
- 字段级折叠；
- 自动保存或明确的保存中/失败状态；
- 同一屏对照历史病历的能力。

#### P0-6：诊疗方案缺少整体校验与提交摘要

当前底栏只显示“保存草稿、完成就诊”。医生无法在提交前快速确认：

- 已开处方、检验、影像、医嘱的数量；
- 待付款金额和没有价格的项目；
- 用药安全阻断或需要豁免的规则；
- 是否仍有未保存的下单草稿；
- 下游将生成哪些收费项和任务。

#### P0-7：测试与现状不一致

`e2e/tests/closed-loop-a.spec.ts:150` 仍等待“医生工作台”标题，但当前模板已注释标题；测试注释还声明完成后自动跳转病历详情，而当前 `onComplete` 只重载预约。现有 E2E 也没有覆盖从医生工作台直接开处方、检验、影像、医嘱的闭环。

### 2.3 P1 问题

- 左侧候诊项仍是原生 `<button>`，卡片、滚动区和 409 弹层为自定义实现，没有充分复用 `FaCard`、`FaScrollArea`、`FaModal`；
- 处方和检验状态直接展示 raw status，缺少统一中文状态映射；
- `recentEncounters` 的“未签署”统计语义使用 `archive_status`，而页面展示主要使用 encounter status，需统一状态口径；
- 页面文件已达约 848 行，数据获取、状态机、病历编辑、下单表单、布局耦合在一个组件中，继续堆逻辑会快速失控；
- 当前 `BusinessCatalogItemPicker` 只向外提供 id，页面为回填名称/单位额外直查 Supabase，应该让选择器返回受控 DTO；
- 右侧只加载检验，没有把影像、医嘱、收费明细和患者旅程 blockers 纳入同一视图。

### 3.2 中等宽度布局（内容区 1024–1359px）

- 左栏缩为 208–224px；
- 右侧诊疗方案缩为 300–320px；
- 患者安全条只保留一行高频信息，次要信息进入悬浮详情；
- 病历字段使用两列栅格，但长文本字段可横跨两列；
- 禁止让病历编辑区低于 480px；低于阈值时自动进入窄桌面模式。

### 3.3 窄桌面布局（内容区 < 1024px）

- 病历编辑区独占主体；
- 候诊队列通过左侧 `FaDrawer` 打开；
- 诊疗方案通过右侧 `FaDrawer` 打开，底栏显示草稿数量和阻断徽标；
- 不把三栏硬挤在一行，不支持只靠横向滚动解决；
- 移动端只支持查看/应急轻量操作，完整问诊仍以桌面端为主。

## 4. 详细交互设计

### 4.1 顶部患者安全条

选中患者后固定在三栏上方，单行优先展示：

1. 宠物姓名、头像、物种/品种、性别、年龄、体重；
2. 主人姓名、电话，点击可复制或展开客户摘要；
3. 分诊等级和生命体征异常；
4. 过敏、慢病、风险标签、性格和医疗备注；
5. 本次旅程阶段、待付款、未完成任务和阻断数。

过敏/危急信息使用危险色且不可被折叠隐藏；普通备注采用 `FaHoverCard` 或 `FaPopover` 展开。无风险时只显示简短“无已知风险”，避免占用整行高度。

### 4.2 左侧候诊与历史

候诊列表直接消费 `GET /workbenches/doctor`，按状态分为紧凑分段：

- 待叫号：主动作“叫号”；
- 已叫号：主动作“开始接诊”；
- 诊疗中：主动作“继续问诊”；
- 辅助徽标：队列号、分诊等级、等待时长、预约原因、医生/诊室。

队列项点击行为必须经过统一 dirty guard。当前患者使用清晰选中态，不再直接展示 raw status。列表使用 `FaScrollArea`，最近病历改为当前宠物历史摘要，并支持在不离开当前页面的抽屉中查看，默认不抢占候诊高度。

### 4.3 中间病历编辑区

按“医生书写顺序”重排并压缩：

- 第一行：主诉（2/5）+ 现病史（3/5）；
- 第二行：体格检查（3/5）+ 诊断（2/5）；
- 第三行：治疗方案（4/5）+ 复诊日期（1/5）；
- 高级/低频字段放入 `FaCollapsible`，不占首屏；
- 多行内容统一使用 `FaTextarea`，单行使用 `FaInput`；
- 问诊问题库、常用诊断、病历模板以紧凑快捷条插入当前字段，插入前保留光标位置；
- `Ctrl/Cmd + S` 保存，保存状态显示“编辑中/保存中/已保存时间/保存失败/版本冲突”；
- 自动保存建议采用停止输入 2 秒后触发，提交方案前必须再次显式保存；签署病历不做静默自动操作。

历史病历采用侧边预览，不直接跳转详情页；医生可以将历史诊断或方案复制到当前草稿，但必须明确提示“已复制，尚未保存”。

### 4.4 右侧诊疗方案区

使用 `FaTabs` 固定四个页签，页签标题带当前就诊数量：

1. **处方**：药品、剂量、频次、途径/用法、疗程、数量、单位、备注；复杂明细使用 `vxe-table`，支持连续新增和键盘移动；
2. **检验**：目录项目、样本/备注、临床问题；支持常用组合；
3. **影像**：检查项目、影像类型、部位/临床问题；在当前页创建，不再默认跳影像工作台；
4. **医嘱**：类型、项目、剂量、频次、数量、单位、执行说明、计划时间、执行人。

每个页签采用“上方已下项目紧凑列表 + 下方快速编辑器”，新增完成后不关闭整个工作区。每条项目展示：中文状态、数量、单价/金额、执行岗位、错误或警告、删除/取消动作。

`BusinessCatalogItemPicker` 应扩展 `change` 事件返回 `{ id, name, unit, billingType, defaultPrice, effectivePrice, active }`，避免页面为名称、单位和价格再次直查 Supabase。

### 4.5 提交诊疗方案

底部 `WorkflowFixedBar` 固定展示：

- 病历保存状态；
- 未提交草稿项数；
- 已创建医疗单据数；
- 预计待收费金额和无价格项目数；
- 用药安全阻断/普通警告数；
- “保存草稿”“提交诊疗方案”“签署病历/稍后签署”。

点击“提交诊疗方案”打开紧凑确认摘要，而不是重复展示完整表单。确认内容包括处方、检验、影像、医嘱、收费、下游岗位和阻断项。存在以下情况时禁止提交：

- 病历保存失败或版本冲突；
- 药物安全存在未处理 blocking check；
- 需要计费的目录项目无有效价格；
- 下单草稿字段不完整；
- 当前 encounter 已关闭、取消、转诊或病历已签署只读。

提交成功后留在当前工作台并自动选中下一位候诊患者；是否自动选择下一位应由用户设置控制，默认只返回队列、不自动开始接诊。

## 6. 数据与接口改造计划

### 6.1 统一读模型

扩展现有接口，而不是再增加浏览器拼装：

```http
GET /workbenches/doctor?storeId=...
GET /clinical/encounters/:id/workspace
```

`doctor workbench` DTO 增加或规范：

- queue id/no/status/priority/waitingAt/room；
- appointment id/reason/scheduledAt；
- encounter id/clinicalStatus/archiveStatus/version；
- pet/customer 最小摘要；
- triage acuity 与高风险标记；
- primaryAction/allowedActions；
- counts 使用中文可映射的稳定 key。

`encounter workspace` DTO 增加：

- pet/customer 完整安全摘要；
- 当前宠物最近病历摘要；
- medicalOrders；
- prescriptionItems 或处方明细摘要；
- lab/imaging 的业务状态和结果摘要；
- 价格/收费汇总；
- medicationSafety checks/warnings；
- allowedActions、blockers、journeyStage、nextOwnerRole；
- `workspaceVersion` 或各实体更新时间，用于刷新与并发判断。

前端选中患者后只请求一次 workspace；处方、检验、影像、医嘱命令成功后可先局部更新，再后台刷新 workspace 校准。

### 6.2 命令边界

继续遵循“浏览器查询可直连 Supabase，业务 Command 必须走 Hono + PostgreSQL RPC”，本次应进一步减少工作台直连查询。

已有命令继续保留：

- 更新病历（expectedVersion）；
- 保存/开具处方；
- 创建检验、影像申请；
- 创建/取消医嘱；
- 叫号、开始接诊；
- 完成问诊。

所有关键写操作必须：

- 使用请求级 idempotency key；
- 服务端按 encounter 解析 tenant/store 并执行 `requireScopedPermission`；
- RPC 内锁定 encounter/相关单据，禁止前端传入租户或价格作为最终真值；
- 写入患者旅程事件和审计；
- 由服务端读取门店有效价格、生成收费项和下游任务。

### 6.3 “诊疗方案篮”提交方式

推荐新增单一 Hono Command：

```http
POST /clinical/encounters/:id/plan/commit
Idempotency-Key: <uuid>
```

请求只提交医生确认的草稿项目与病历 `expectedVersion`，服务端调用统一 PostgreSQL RPC，在一个事务中完成：

1. 校验 encounter 状态、医生作用域、版本号；
2. 更新病历草稿；
3. 创建/更新处方并执行开具规则；
4. 创建检验、影像、医嘱；
5. 生成收费明细、岗位任务、患者旅程事件；
6. 执行用药安全检查；
7. 将 encounter 推进到 `plan_ready`；
8. 返回 workspace 最新快照或变更摘要。

任何一项失败整体回滚，避免“处方成功但检验失败”造成医生误判。实现时应把现有单项 RPC 的共享数据库逻辑提取为可在同一事务内调用的内部函数，不在 Hono 中串行调用多个 HTTP Command 假装原子。

若本期无法安全完成批量事务，P0 允许先采用“单项立即提交 + 明确提交状态”的方式上线，但“提交诊疗方案”必须阻止存在失败/未提交草稿时结束问诊，且计划篮批量事务列为紧随其后的 P0.1，不得用前端静默重试掩盖部分成功。

## 7. 权限、安全与状态规则

- 页面可见：`encounter.work`；只读历史：`encounter.view`；
- 处方开具：`prescription.create` + `prescription.issue`，受控药额外校验既有权限；
- 检验/影像申请：对应 order 权限；
- 医嘱：应增加/核对医生开立权限，不应复用护士查看权限作为创建权限；
- 用药安全阻断豁免：`medication_safety.override` + 必填原因 + 审计；
- 已签署病历只读，修订仍走现有修订流程；
- 已关闭/取消/转诊 encounter 禁止新增医疗单据；
- 前端的 `allowedActions` 仅控制交互，后端必须重复校验；
- 不在工作台展示候诊大屏之外的非必要敏感字段，电话等信息按员工权限展示。

## 11. E2E 核心场景

1. **标准问诊闭环**：签到/候诊 → 叫号 → 接诊 → 病历 → 处方 + 检验 + 影像 + 医嘱 → 提交 → 断言四类单据、收费、任务、事件；
2. **幂等重试**：提交时模拟超时并重复请求，断言每类单据和 charge item 只有一份；
3. **原子回滚**：让一个无效/无权限项目失败，断言病历状态和其他下单没有部分提交；
4. **用药安全阻断**：命中 blocking rule，普通医生不能提交；有权限且填写原因后成功并产生 override 审计；
5. **并发病历**：两个页面编辑同一 encounter，第二个保存得到 409，验证三种冲突动作；
6. **草稿保护**：编辑病历或新增未提交医嘱后切患者、切门店、离开路由和刷新；
7. **状态只读**：签署/关闭/取消/转诊就诊不能新增项目；
8. **响应式**：在 1280 与 1440 视口完成核心流程，验证 Drawer 和固定底栏；
9. **价格异常**：目录项目无门店有效价时显示明确错误，不能静默以 0 元提交；
10. **队列连续处理**：完成一位患者后返回队列，下一位患者上下文不混入上一位草稿或订单。

## 12. 风险与非目标

### 12.1 主要风险

- 新旧 `encounters.status/archive_status/clinical_status` 并存，实施前必须固化页面状态口径；
- `plan/commit` 跨处方、诊断、医嘱、收费、任务多个域，不能简单复制现有 Hono handler，需要数据库层可组合事务设计；
- 用药安全 migration 已静态集成但运行时门禁仍需在真实 Supabase 环境验证；
- 现有工作台和统一岗位工作台入口重复，导航层需明确“岗位队列入口”和“医生临床工作区”的跳转关系；
- 自动保存若处理不当会放大 409 频率，必须串行化保存请求并取消过期响应写回。

### 12.2 本次非目标

- 不修改 Fantastic Admin 内建组件；
- 不引入 Element Plus；
- 不让 AI 自动诊断或自动开方；
- 不在医生工作台实现检验/影像岗位的采集、审核、发布全流程；医生只申请和查看结果摘要；
- 不用前端跨表聚合替代服务端 workspace；
- 不把病历签署与“结束问诊/提交诊疗方案”强制合并，允许稍后签署但必须显著提示待签署状态。

## 13. 完成定义

本改造只有在医生能在 `/clinical/workbench` 内完成一位真实患者的接诊、病历、四类下单和诊疗方案提交，并通过数据库验证收费、任务、旅程事件、幂等与原子性后，才视为完成。仅调整间距、改成三栏、增加跳转按钮或补几个弹窗，均不满足本计划的完成定义。
