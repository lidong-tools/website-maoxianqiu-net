# 岗位工作界面高密度交互改造计划

> 目标应用：`apps/maoxianqiu`  
> 目标路由：`/workbenches/:role`  
> 当前页面：`apps/maoxianqiu/src/views/workbenches/index.vue`  
> 覆盖岗位：前台、分诊、医生、护士、检验、影像、收银、药房、回访、管理  
> 优先级：P0

## 1. 改造目标

将当前纵向排列的“页头卡片 + KPI 卡片组 + 患者/任务队列卡片”合并为一个高密度、全高的岗位工作区，减少无效留白和重复边框，让业务人员在首屏内完成：

1. 切换当前岗位；
2. 查看各状态待办数量；
3. 搜索、筛选并定位患者或任务；
4. 直接执行当前业务状态下的主动作；
5. 在不离开队列的情况下查看患者和任务详情；
6. 连续处理下一条待办，并保留筛选、页码和滚动位置。

目标结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ [岗位选择] [搜索患者/单号] [状态数量筛选]        [刷新] 总数 │
├──────────────────────────────────────────────────────────────┤
│ 紧凑业务表格：患者 / 任务 / 状态 / 时效 / 执行人 / 主动作   │
│                                                              │
│                                      点击行 → 右侧详情抽屉   │
├──────────────────────────────────────────────────────────────┤
│ 分页 / 加载状态                                              │
└──────────────────────────────────────────────────────────────┘
```

## 2. 当前实现问题

### 2.1 三个纵向区块降低信息密度

当前页面依次展示：

1. 岗位名称、说明、岗位选择和刷新按钮组成的页头卡片；
2. 每个状态一个 `FaCard` 的 KPI 卡片组；
3. “患者与任务队列”卡片。

这三个区块均有独立边框、内边距和纵向间距，导致真正需要操作的队列被推到首屏下方。KPI 卡片只展示状态名称和数字，却占用整行高度，无法直接参与筛选。

### 2.2 队列使用重复卡片

每条记录使用 `p-3 border rounded-lg` 卡片展示，存在以下问题：

- 行高偏大，同一屏只能看到少量记录；
- 患者、状态、等待时间、执行人分散为多行；
- “患者上下文”和主动作并列，占用操作区宽度；
- 所有记录共享一个 `actionLoading`，单条操作可能让整页按钮进入 loading；
- 没有搜索、分页和岗位专属列；
- 点击记录本身没有详情行为，必须寻找按钮。

### 2.3 统计和列表没有形成联动

当前 `counts` 只用于生成展示卡片，点击状态数量无法筛选列表。服务端的数量又基于当前截取的列表计算，不能保证代表完整业务范围。

### 2.4 不同岗位使用同一信息模板

十类岗位的数据重点并不相同：

- 前台、分诊、医生关注队列号、预约原因、分诊级别和等待时长；
- 护士、检验、影像、药房关注任务项目、来源、优先级、截止时间和执行人；
- 收银关注收费项目、来源单据、金额和支付状态；
- 管理人员关注超时、异常和责任岗位。

当前页面使用一套通用卡片，无法针对岗位提高有效信息密度。

## 3. 页面结构改造

### 3.1 合并页头和统计区

- 删除独立页头卡片，不再占用一整行展示标题和描述；
- 将岗位选择、搜索、刷新和总数合并为约 44px 高的顶部工具栏；
- KPI 卡片改为带数量的状态筛选，例如“全部 26、待领取 12、执行中 5、失败 2”；
- 状态筛选使用紧凑 `FaTabs`，点击后立即过滤列表；
- 页面外边距调整为 8px，区块间距控制在 8px；
- 页面采用全高 `flex` 布局，表格占据工具栏之外的全部剩余空间；
- 只保留一个主 `FaCard` 或等价业务容器，避免层层嵌套卡片。

### 3.2 使用紧凑岗位表格

使用 `FaTable` 替换逐条卡片，推荐行高约 44–52px。

岗位列定义：

| 岗位类型 | 表格列 |
|---|---|
| 前台/分诊/医生/管理 | 队列号、宠物/主人、预约或主诉、分诊/优先级、状态、等待时长、操作 |
| 护士/检验/影像/药房/回访 | 任务项目、宠物/主人、来源、优先级、状态、截止时间、执行人、操作 |
| 收银 | 宠物/主人、收费项目、来源单据、金额、状态、创建时间、操作 |

统一显示规则：

- 宠物与主人合并为一个单元格，宠物为主信息，主人和电话为次信息；
- 状态使用 `EntityStatusTag` 和既有中文标签、颜色映射；
- 等待时间和截止时间根据普通、预警、超时显示不同颜色；
- 业务单号、队列号和金额使用等宽数字或 `tabular-nums`；
- 优先级只在非普通或需要关注时突出显示；
- 次要信息使用 Tooltip，不通过增加行高完整展开。

### 3.3 操作区收口

- 每行只显示一个当前状态下最重要的主动作；
- 次要动作放入 `TablePrimaryAction` 的更多菜单；
- 操作 loading 精确到当前行和动作，禁止锁住整张表；
- 点击操作按钮时阻止行点击，避免同时打开详情抽屉；
- 主动作继续由业务状态决定：叫号、开始接诊、领取任务、开始执行、完成任务、加入结算等；
- 前端只根据 `allowedActions` 控制显示，后端仍执行权限和状态校验。

## 4. 搜索、筛选与连续处理

### 4.1 搜索

顶部工具栏增加搜索框，支持：

- 宠物名称；
- 主人姓名和电话；
- 队列号；
- 任务标题和项目名称；
- 预约、收费、处方、检验、影像等业务单号。

搜索采用 300ms 防抖。搜索词或状态变化后重置到第一页，由服务端执行搜索，不允许只在前端对已加载的固定数量记录过滤。

### 4.2 状态筛选

- 状态数量直接作为筛选入口；
- 状态顺序按各岗位工作流固定排列，而不是按对象键顺序；
- 增加“全部”状态；
- 当前状态使用明显选中态；
- 状态数量来自完整业务范围，不受当前分页大小影响；
- 切换岗位后恢复该岗位的默认状态筛选。

### 4.3 路由状态

以下状态同步到路由 query：

```text
status
keyword
page
pageSize
```

刷新页面、进入详情后返回或使用浏览器前进/后退时，必须恢复岗位、筛选、搜索和页码。当前岗位继续使用既有 Pinia 偏好持久化。

### 4.4 操作后的列表行为

- 命令成功后先局部更新当前行，再后台刷新状态数量和当前页；
- 若状态变化导致记录不再属于当前筛选，短暂显示成功反馈后移除该行；
- 保留当前滚动位置、搜索条件和分页；
- 刷新按钮只重新加载数据，不重置用户上下文；
- 命令失败时保留记录和详情抽屉，显示可理解的错误信息；
- 409 状态冲突时刷新该行最新状态，并提示用户重新确认操作。

## 5. 右侧详情抽屉

点击表格行打开宽约 560px 的 `FaDrawer`，避免为了查看上下文频繁跳转页面。

### 5.1 通用内容

- 宠物、主人和联系电话；
- 当前状态、优先级和来源岗位；
- 等待时间或截止时间；
- 业务单号、创建时间和最近操作人；
- 当前主动作和允许的次要动作。

### 5.2 岗位内容

- 队列岗位：预约原因、分诊等级、生命体征、风险标记、候诊轨迹；
- 医疗执行岗位：任务项目、执行要求、来源医嘱/申请、执行人和异常记录；
- 收银岗位：收费明细、来源单据、数量、单价、金额和异议状态；
- 管理岗位：异常原因、超时阶段、责任岗位和处理记录。

存在 `encounterId` 时，通过现有 workspace 接口加载患者上下文、旅程阶段、收费、任务和 blockers。

### 5.3 抽屉操作

- 抽屉底部固定主动作和次要动作；
- 抽屉和表格行共用同一动作配置，禁止维护两套判断；
- 分诊录入直接放入抽屉，使用紧凑双列表单和固定保存栏；
- 收银异议作废继续使用 `FaModal` 二次确认并要求填写原因；
- 完整专业流程通过明确入口进入对应业务页；
- 关闭抽屉后保留列表滚动位置和筛选条件；
- 抽屉加载失败只影响抽屉，不清空主列表。

## 6. 前端组件结构

页面拆分为职责组件，而不是三个纵向展示卡片：

```text
views/workbenches/
├── index.vue
├── components/
│   ├── WorkbenchToolbar.vue
│   ├── WorkbenchTable.vue
│   └── WorkbenchDetailDrawer.vue
└── composables/
    └── useRoleWorkbench.ts
```

职责划分：

- `index.vue`：全高布局、路由状态和组件编排；
- `WorkbenchToolbar.vue`：岗位、搜索、状态数量、刷新；
- `WorkbenchTable.vue`：岗位列配置、状态展示和主动作；
- `WorkbenchDetailDrawer.vue`：上下文详情、次要操作和专业页面入口；
- `useRoleWorkbench.ts`：查询参数、请求、局部更新、行级 loading 和错误恢复。

表格列通过岗位配置生成，禁止在模板中堆积十套大型条件分支。

优先使用：

- `FaTable`：紧凑队列；
- `FaTabs`：状态数量筛选；
- `FaSearchBar`：统一搜索；
- `FaDrawer`：详情与非破坏性编辑；
- `FaModal` / `useFaModal`：破坏性确认；
- `FaEmpty`：空状态；
- `TablePrimaryAction`：主动作和更多菜单；
- `useFaToast`：结果反馈。

不得修改 `packages/components/`，不得新增 Element Plus。

## 7. API 与类型调整

扩展现有岗位工作台接口：

```http
GET /workbenches/:role
  ?storeId=
  &status=
  &keyword=
  &page=1
  &pageSize=50
```

返回结构：

```ts
interface WorkbenchData {
  role: WorkbenchRole
  counts: Record<string, number>
  total: number
  page: number
  pageSize: number
  list: WorkbenchRow[]
}

interface WorkbenchRow {
  id: string
  status: string
  priority?: string
  customer?: JourneyPerson | null
  pet?: JourneyPerson | null
  assignee?: JourneyPerson | null
  display: {
    businessNo?: string
    title: string
    subtitle?: string
    sourceLabel?: string
  }
  timing: {
    startedAt?: string | null
    dueAt?: string | null
    elapsedMinutes?: number
    overdue?: boolean
  }
  primaryAction?: string
  allowedActions: string[]
  detailTarget?: {
    type: 'encounter' | 'queue' | 'task' | 'charge'
    id: string
  }
}
```

实现要求：

- 移除 `WorkbenchRow` 的宽泛 `[key: string]: unknown`，建立公共字段和岗位扩展 DTO；
- 状态数量为当前门店、岗位和搜索范围的全量聚合，不受分页影响；
- 关键词查询由服务端完成；
- 默认排序为优先级降序、超时/临期优先、等待或创建时间升序；
- 继续按租户、门店和岗位执行 `requireScopedPermission`；
- 主动作继续调用现有 queue、task、billing Command；
- 关键写操作继续携带幂等键；
- 浏览器不得重新跨表拼装工作台数据。

## 8. 响应式与视觉规范

### 桌面端

- 1440px 及以上展示完整列；
- 1280px 隐藏来源说明、次要时间等低优先级列；
- 操作列固定在右侧并明确设置宽度；
- 表头固定，表体独立滚动；
- 首屏应显示工具栏、状态筛选、表头和至少 8–12 条记录。

### 窄屏

- 优先保留业务对象、状态、时效和主动作；
- 隐藏次要列，通过详情抽屉查看完整内容；
- 不恢复为纵向大卡片列表；
- 不允许页面级横向滚动；确需横向滚动时只发生在表格内部。

### 视觉密度

- 工具栏高度约 44px；
- 表格表头约 40px；
- 数据行约 44–52px；
- 主内容外边距 8px；
- 组件间距以 8px 为主；
- 同一信息只显示一次，避免标题、状态和对象名称在多个区块重复。

## 9. 实施阶段

### Phase 1：布局与状态筛选

- 合并页头、岗位选择和状态数量；
- 改造全高页面容器；
- 将 KPI 卡片变为可点击状态筛选；
- 保留现有中文状态和来源映射。

### Phase 2：岗位表格

- 建立三类岗位列配置；
- 接入 `FaTable`、状态标签和行级主动作；
- 将全局 action loading 改为行级 loading；
- 增加固定表头、独立滚动和响应式列。

### Phase 3：搜索与分页 API

- 扩展工作台查询参数和强类型 DTO；
- 实现服务端关键词查询、全量状态计数和分页；
- 将筛选状态同步到路由 query；
- 实现操作后的局部更新和后台刷新。

### Phase 4：详情抽屉

- 实现通用详情抽屉；
- 接入 encounter workspace；
- 将分诊表单整合到抽屉；
- 建立专业页面跳转和错误恢复。

### Phase 5：验证与收口

- 验证全部十类岗位；
- 完成不同宽度和长队列测试；
- 完成真实 Command、数据库状态和权限闭环；
- 对比改造前后的首屏记录数和操作步骤。

## 10. 验收标准

### 功能验收

- [ ] 十类岗位均使用同一紧凑框架，并展示岗位专属列；
- [ ] 状态数量可以直接筛选列表；
- [ ] 状态数量等于服务端完整业务范围数量；
- [ ] 搜索支持患者、电话、队列号、任务、项目和业务单号；
- [ ] 点击行打开详情抽屉；
- [ ] 点击行内动作不会同时打开抽屉；
- [ ] 叫号、接诊、领取、执行、完成、结算和作废命令行为保持正确；
- [ ] 单条操作不会锁定其他行；
- [ ] 刷新、返回页面后保留岗位和筛选上下文；
- [ ] 状态冲突、越权和接口失败不会导致列表上下文丢失。

### 布局验收

- [ ] 不再存在页头、KPI、队列三个纵向大卡片；
- [ ] 1280、1440、1920 宽度首屏均可看到主要队列数据；
- [ ] 1280 宽度首屏至少展示 8 条记录；
- [ ] 1440 及以上首屏至少展示 10–12 条记录；
- [ ] 主动作列始终可见；
- [ ] 长文本不会无限撑高表格行；
- [ ] 表格和抽屉在浅色、深色主题下均清晰可用。

### 工程验收

- [ ] 使用 Vue 3 `<script setup lang="ts">`；
- [ ] 工作台核心 DTO 不使用 `any` 或宽泛索引签名；
- [ ] 使用 UnoCSS，不新增 Element Plus；
- [ ] 不修改 Fantastic Admin 内建组件；
- [ ] 新增函数具有业务意图注释；
- [ ] 前端和 API typecheck、`pnpm lint`、生产构建通过；
- [ ] Playwright 使用真实 Hono Command 和 Supabase 数据状态断言。

## 11. 测试场景

1. 分别登录十类岗位，验证可用岗位、默认状态和专属列；
2. 切换状态筛选，验证计数和服务端真实数据一致；
3. 使用宠物、主人、电话、队列号和业务单号搜索；
4. 切换岗位、搜索、翻页后刷新页面，验证路由状态恢复；
5. 点击行打开抽屉，点击主动作仅执行命令；
6. 验证叫号、开始接诊、领取、开始执行和完成任务；
7. 验证收银加入结算与异议作废；
8. 并行操作两个不同行，验证 loading 相互独立；
9. 模拟状态冲突、接口失败和越权，验证错误恢复；
10. 在 1280、1440、1920 宽度验证信息密度和表格滚动；
11. 使用 100 条以上数据验证分页、状态计数和搜索准确性；
12. 从专业业务页返回工作台，验证筛选和滚动上下文保留。

## 12. 实施约束

- 本次覆盖所有岗位，不只优化某一个角色；
- 采用“工具栏 + 状态筛选 + 表格 + 右侧详情抽屉”方案；
- 不改变患者旅程状态机、岗位权限和既有专业业务页面；
- 不将状态筛选重新设计为大面积统计卡片；
- 不通过减少必要业务信息制造视觉简洁；
- 当前工作树中的中文状态与来源映射属于已有改动，实施时必须保留；
- 页面只有在首屏记录数、连续操作效率和错误恢复均达到验收标准后才视为完成。
