### 3.2 阻断问题

#### D-P0-1：原子提交 migration 无法按当前函数签名创建

`supabase/migrations/20260810000301_clinical_plan_commit.sql:10-22` 中，`p_encounter_updates` 至 `p_finish_consultation` 参数带默认值，后面的 `p_actor_employee_id`、`p_actor_role`、`p_source_workbench`、`p_request_id`、`p_idempotency_key` 不带默认值。

PostgreSQL 要求一个输入参数出现默认值后，后续输入参数也必须有默认值。因此该 `CREATE FUNCTION` 会报“带默认值参数之后的输入参数也必须有默认值”，导致 `commit_clinical_plan` 无法部署。计划要求的单事务提交边界由此不可用。

#### D-P0-2：新 RPC 未纳入 service-role-only 安全管控

- `commit_clinical_plan` 未加入 `api/lib/service-rpc-manifest.ts`；
- migration 结尾未对该函数执行 `REVOKE ... FROM PUBLIC/anon/authenticated` 与仅向 `service_role` 授权；
- `pnpm check:rpc-manifest` 明确失败并列出 `commit_clinical_plan`。

该问题同时违反项目 service role RPC 约束和计划的权限安全验收要求。

#### D-P0-3：无有效价格项目没有阻止提交

workspace 与提交摘要已计算和显示 `billing.noPriceCount`，但 `onRequestCommitPlan` 仅检查 encounter 只读、病历保存和 medication safety blocking，没有在 `noPriceCount > 0` 时阻止提交；数据库计划提交函数中也未发现对应拒绝逻辑。

这不满足计划中“需要计费的目录项目无有效价格时禁止提交”。

#### D-P0-4：用药安全豁免无法在当前工作台闭环

页面能显示 blocking check，并提示“请先处理豁免”，但当前工作区没有填写豁免原因、执行 override、生成豁免审计的交互与命令。命中阻断后医生仍需离开或无法继续，不满足计划的同屏闭环及 E2E 场景。

#### D-P0-5：幂等键契约不一致

`apps/maoxianqiu/src/api/modules/patient-journey.ts:28-35` 在 body 和 `idempotency-key` header 中分别生成了两个 UUID。服务端优先使用 header，虽然一次 Axios 请求内部仍有键，但 body/header 表达的是不同请求身份，不利于明确重试、日志追踪和客户端复用。

此外，该方法把 RPC 返回的“提交结果摘要”断言成 `EncounterWorkspace`，实际调用方随后另行刷新 workspace，类型契约不准确。

#### D-P0-6：目录查询会漏掉没有门店覆盖行的有效项目

`CatalogItemPicker` 使用 `store_catalog_items!inner`。内连接要求目录项目必须存在门店覆盖记录，因此没有覆盖行、原本应回退到 `default_price` 的项目不会出现在结果中，与计划中的 `custom_price ?? default_price` 有效价语义不一致。

### 4.2 阻断问题

#### R-P0-1：状态筛选污染“全量状态计数”

`api/routes/patient-journey.ts:148-161` 先把：

```ts
const activeStatuses = status ? [status] : statuses
```

随后计数查询、总数查询和分页查询全部使用 `activeStatuses`。当用户点击某一状态后，服务端只统计该状态；其他状态数量会变成 0，前端“全部”也只剩当前状态数量。

计划要求状态数量来自当前门店、岗位和搜索范围的完整业务范围，且不受当前状态筛选和分页影响。当前实现不符合该核心验收项。

#### R-P0-2：岗位工作台 API 类型检查失败

本次新增/改造的 `patient-journey.ts` 产生 3 个 API TypeScript 错误，已在 2.2 节列出。计划工程验收明确要求 API typecheck 通过，因此当前不能验收。

#### R-P0-3：相关 service RPC 未通过 manifest 管控检查

`check:rpc-manifest` 报告 `check_in_clinical_patient`、`record_clinical_triage`、`transition_clinical_queue`、`transition_workflow_task`、收费项与发票相关 RPC 等没有纳入 service-role-only manifest。这些 RPC 是岗位工作台主动作所依赖的业务命令，安全门禁检查失败时不能判定命令链路完成。
