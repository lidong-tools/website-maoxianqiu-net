## 8. Phase 2 决策回顾

> 以下决策基于 Stage-01 已完成的 10/10 业务领域代码实现、PRD v0.4 和 09-业务流程与状态机.md 推断得出。
> 状态 `accepted` 表示该决策已在代码或正式文档中隐式落地，但此前未在 ADR 中显式记录。
> 状态 `proposed` 表示仍无法从现有实施中推断，需要产品/业务方确认。

### 8.1 P0 业务决策回顾

#### ADR-BIZ-001：第一批客户是否支持连锁多门店

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：第一批客户是单店还是连锁？
- 决策：**支持连锁（多门店）**
- 原因：PRD §4 定义 tenant → stores 多层级模型；04 文档 Phase 2 已完成 tenants/stores/employee_store_assignments 实现；RLS 测试覆盖多门店隔离（rls_tenant_store.sql）
- 影响：首版即需完整 tenant 上下文字段（所有业务表含 tenant_id + store_id），不能简化为单店硬编码
- 依据：PRD §4.1、04 文档 §17.1

#### ADR-BIZ-002：是否立即引入完整 tenant

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：是否立即引入完整 tenant，还是先把现有所有数据归入默认 tenant？
- 决策：**立即引入完整 tenant 模型**
- 原因：Phase 2（Foundation/IAM）已完成 tenants 表、tenant_memberships、employees、employee_store_assignments、employee_role_assignments 全链路；所有业务 migration（00014~00022）均含 tenant_id 列和 RLS 策略
- 影响：无默认 tenant 的临时方案，所有数据从第一天起租户隔离
- 依据：04 文档 §4、§17.2 migration 00014~00022

#### ADR-BIZ-003：同租户跨店客户与病历共享

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：同租户是否跨店共享客户和病历？
- 决策：**租户级主档、门店级关系（customer_store_relations 模型）**
- 原因：PRD §4.4 明确定义"客户和宠物建议采用租户级主档、门店级关系"；03 数据模型已定义 customer_store_relations 表含 first_visit_at/last_visit_at/visit_count
- 影响：默认员工仅能查看授权门店的就诊和交易记录；需"跨店客户查看"权限方可查看租户内完整客户视图
- 依据：PRD §4.4、03 文档 §3.2

#### ADR-BIZ-004：医生跨店查看历史医疗记录

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：普通医生是否可以跨店查看历史医疗记录？
- 决策：**默认不可，需分配"跨店客户查看"权限**
- 原因：PRD §4.4 明确"有'跨店客户查看'权限的角色可查看租户内完整客户视图"，且"医疗记录跨店查看必须记录审计日志"
- 影响：权限模型中需包含 medical_record.read.tenant 与 medical_record.read.store 粒度区分
- 依据：PRD §4.4、§5.3 权限模型

#### ADR-BIZ-005：首版登录方式优先级

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：首版登录方式：邮箱、手机号、微信，优先级是什么？
- 决策：**邮箱优先（Supabase Auth 默认方式）**
- 原因：当前代码基线为 Supabase Auth 邮箱/密码登录（PRD §0.1）；未集成手机号（SMS）或微信 OAuth
- 影响：MVP 阶段仅邮箱注册/登录/找回密码；手机号和微信登录接入时间取决于后续需求
- 依据：PRD §0.1、当前代码实现（Supabase Auth）

#### ADR-BIZ-006：首版支付方式

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：首版支付仅记录线下收款，还是接微信/支付宝？
- 决策：**首版仅记录线下收款（现金/银行卡/储值/组合支付）**
- 原因：PRD §16.2 明确"首版可先记录支付，不必接支付网关；但数据模型必须支持外部支付流水号"
- 影响：billing migration 00020 的支付模型已预留 external_payment_id 字段，后续接入支付网关时无需改表
- 依据：PRD §16.2

#### ADR-BIZ-007：会员储值、积分、折扣是否进入首版

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：会员储值、积分、折扣是否进入 MVP？
- 决策：**进入首版**
- 原因：Operations 领域（MXQ-12001~12009）已于 2026-08-06 交付，migration 00018 包含 membership_tiers、membership_discount_rules、loyalty_accounts、loyalty_transactions 表；PRD §17 虽标注为 V1，但实际开发已覆盖
- 影响：已超出 PRD 原定的 MVP/V1 划分，首版交付即含会员和积分能力
- 依据：04 文档 §17.1、migration 00018

#### ADR-BIZ-008：住院、寄养、美容是否进入首版

- 日期：2026-08-07（回顾）
- 状态：**accepted（部分）**
- 问题：住院、寄养、美容是否进入第一阶段销售版本？
- 决策：**住院和寄养进入首版；美容暂作为 catalog_item 类型支持，未设独立领域**
- 原因：Inpatient 领域（MXQ-11001~11009）已于 2026-08-06 交付，migration 00021 含 rooms/cages/admissions/nursing；catalog_items 类型含 grooming，但无独立美容预约/服务记录模块
- 影响：住院和寄养是首版正式功能；美容可收费但缺少专属工作流
- 依据：04 文档 §17.1、migration 00016 catalog、migration 00021 inpatient

#### ADR-BIZ-010：是否需要从小暖或其他系统迁移

- 日期：2026-08-07（回顾）
- 状态：**accepted**

- 决策：**需要支持从旧系统导入，已实现导入框架**

- 依据：PRD §30、migration 00018

### 8.2 P0 技术迁移决策回顾

#### ADR-TECH-001：store_members 迁移策略

- 日期：2026-08-07（回顾）

### 8.3 打印与设备决策回顾

#### ADR-PRN-001：小票规格

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：小票规格：58mm、80mm、A4？
- 决策：**全部支持，作为可配置参数**
- 原因：PRD §27.1.3 将三种规格均列为可配置项；print_templates 表的 paper_size 字段支持多尺寸
- 影响：打印模板需兼容三种宽度渲染
- 依据：PRD §27.1.3、03 文档 print_templates 表

#### ADR-PRN-002：必须打印的文档类型

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：必须打印哪些文档：收费单、处方、病历、检验报告、接种证明？
- 决策：**全部需支持打印**
- 原因：PRD §27.1.3 列出的自动打印场景覆盖所有所列文档；print_templates 表的 document_type 字段用于区分模板类型
- 影响：每种文档类型需对应一套打印模板
- 依据：PRD §27.1.3

#### ADR-PRN-003：钱箱联动

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：是否必须联动钱箱？
- 决策：**支持钱箱指令配置，非首版强制功能**
- 原因：PRD §27.1.4 提供钱箱开启指令配置能力，但将硬件直连列为首版不实现项——即通过本地打印代理间接支持
- 影响：store_devices 表需配置钱箱开启指令；是否需要与收费动作自动联动待确认
- 依据：PRD §27.1.4

#### ADR-PRN-004：本地打印代理

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：是否接受安装本地打印代理？
- 决策：**是（通过本地打印代理方案）**
- 原因：PRD §27.1.4 明确"Web SaaS 不直接承诺浏览器自动发现所有设备"，首版方案为浏览器系统打印 + 本地打印代理适配接口
- 影响：需提供打印代理的安装部署文档和 API 规范
- 依据：PRD §27.1.4

#### ADR-PRN-005：离线打印队列

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：是否需要离线打印队列？
- 决策：**需要（已定义打印任务状态机）**
- 原因：09-业务流程与状态机.md §16 明确定义了打印任务状态机：`queued → dispatched → printing → printed`（含失败重试），print_jobs 表含 idempotency_key 字段

### 8.4 医疗业务决策回顾

#### ADR-MED-001：麻醉药/处方药特殊权限

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：是否涉及麻醉药、处方药等特殊权限？
- 决策：**是（处方药需独立权限控制）**
- 原因：PRD §14.3 药品字段含"是否处方药"标记；PRD §5.3 权限模型要求"创建退款与审核退款不能默认授予同一普通角色"，类似原则适用于处方药管控
- 影响：需定义 prescription.controlled_drug 或类似权限码
- 依据：PRD §14.3

#### ADR-MED-002：病历电子签名

- 日期：2026-08-07（回顾）
- 状态：**proposed**（待确认）
- 问题：病历签署是否需要电子签名？
- 决策：**无法推断——PRD 使用"签署"作为病历状态（draft → signed），但未明确是否需要法律级电子签名（CA 证书/时间戳）**
- 原因：当前病历状态机为 draft → signed → revised，signed 仅表示医生确认，不涉及加密签名
- 影响：若需法律级电子签名，需引入第三方 CA 服务

#### ADR-MED-003：检验报告双人审核

- 日期：2026-08-07（回顾）
- 状态：**proposed**（待确认）
- 问题：检验报告审核是否要求双人？
- 决策：**无法推断——PRD §12.2 检验流程为"结果录入 → 审核 → 发布"，未要求录入人和审核人必须不同**
- 原因：当前检验状态机（09 文档 §11）仅区分 result_entered → verification_pending → published，没有双签检查
- 影响：若需双人审核，需在状态转换中增加录入人与审核人不得为同一人的校验

#### ADR-MED-004：危急值确认

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：危急值确认是否进入 MVP？
- 决策：**进入 MVP**
- 原因：PRD §12.2 明确"危急值需要醒目标识与确认记录"；09 文档 §11 检验状态机包含危急值相关流程；migration 00022 diagnostics 含 abnormal_flag 字段
- 影响：危急值必须在前端以醒目方式展示，确认动作需审计
- 依据：PRD §12.2、09 文档 §11

#### ADR-MED-005：疫苗证明监管格式

- 状态：**proposed**（待确认）
- 问题：疫苗证明是否需要监管格式？
- 决策：**无法推断——涉及监管合规，需与客户确认当地动物卫生监督所/海关要求**
- 原因：PRD §29.2 含"接种证明文件"字段，但未定义格式要求

#### ADR-MED-006：宠物死亡记录与数据可见性

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：宠物死亡记录和数据可见性规则？
- 决策：**已定义：宠物死亡后停止自动提醒，历史记录保留且可见**
- 原因：PRD §8 明确"宠物死亡后停止自动提醒，但历史记录保留"；宠物状态含 deceased；死亡后预防保健提醒自动中止（PRD §29.4）
- 影响：死亡宠物数据不归档不删除，仅停止主动触达
- 依据：PRD §8、§29.4

#### ADR-IPT-006：寄养与医疗住院是否共享房间

- 日期：2026-08-07（回顾）
- 状态：**accepted**
- 问题：寄养与医疗住院是否共享房间？
- 决策：**共用房态能力（rooms/cages 统一管理），权限区分**
- 原因：PRD §13.4 明确"住院和寄养共用房态能力，但医疗住院记录与普通寄养权限必须区分"；rooms 表的 room_type 字段包含 '住院'/'隔离'/'ICU'/'寄养' 分类
- 影响：房间列表可按类型过滤；医疗住院数据受更严格权限管控
- 依据：PRD §13.4、migration 00021 rooms
